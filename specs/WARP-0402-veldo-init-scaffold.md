## Intent

PLAN-0004 turns VELDO into an executable system. Feature F4 (adoption) covers the
last mile of a repository actually living the method, and the first friction a
new repository hits is standing up the substrate: the gate, the validator, the
capability manifest, the spec templates, and a plan the moment work starts. X2
removes that friction to one mechanical step. A single call lays the VELDO
substrate from the shipped templates and produces a repository whose own gate is
already green with no product code in it, so a new repository is VELDO-ready and
provably so, not merely populated with files that might or might not gate.

## Context

X2 of PLAN-0004, feature F4, depends on nothing (alongside the other adoption
work). It follows the shipped platform pattern: a stdlib module under .veldo/
(like events.py, metrics.py, lessons.py, release.py), no third-party dependency,
control logic gate-tested in the unit slot with no live surface. The scaffolder
copies the templates rather than restating them, so the gate, validator, and
index generator it lays down are the canon; the one transform it applies is to
fill the template gate's two deliberately-blank slots (unit, dependency_audit)
with an honest na for a fresh repository, which is exactly what makes the
produced gate green on an empty starter plan (XJ2). The interactive /veldo:init
skill remains the front door that configures those slots and the protected paths
with a human; this module is the mechanical scaffolder that skill, or an adopting
human, can call.

## Out of scope

Interviewing a human for the real gate commands or protected paths (that is the
/veldo:init skill, a procedure, not this mechanical step). Configuring server-side
enforcement or branch protection (a host setting, X9 and the branch-protection
recipe). Writing the first real specification or plan for the adopting repository
(the starter plan is a valid placeholder to be replaced, not the real increment).
Migrating or reconciling an existing partial VELDO install beyond the never-
overwrite guarantee.

## Notes

Why the scaffolder is mechanical and not a procedure: laying files from the
templates and producing a green gate is a transaction that runs end to end in the
gate here over a temporary directory with no network, no model, and no product
surface, so its status is mechanical and the selftest proves it by running the
scaffolded gate and requiring green. Configuring the real gate slots with a human
is judgment, so that stays in the init skill as procedure; claiming it as
mechanical would overclaim.

Why the green gate is proven adversarially: the whole value of the feature is
that the produced repository actually gates green on nothing, so the selftest
runs the scaffolded scripts/verify.sh and, to prove the assertion has teeth,
mutates the scaffold in two independent ways - it deletes a required substrate
file (.veldo/validate.py, so the gate's fail-closed contract check turns it red)
and it corrupts the starter plan (so contract validation rejects it) - and
requires the gate to go RED in each case. A scaffolder that laid a red gate, left
a blank slot, or laid an invalid starter plan fails the green assertion; a
re-run that clobbered an authored file fails the sentinel assertion.

The reviewer should confirm by rerunning the selftest and the standalone module:
(1) python3 .veldo/init_scaffold.py <dir> stands up a repository whose
./scripts/verify.sh exits 0; (2) a second run over the same directory creates
nothing and preserves a hand-edited file; (3) deleting a required file or
breaking the starter plan turns the produced gate red; (4) the capabilities entry
is byte-identical across both manifest copies and its status is honest; (5) the
docs, secret, lint, and template-sync gates stay green.
