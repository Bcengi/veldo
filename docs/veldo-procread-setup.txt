The process reader of space management: the owner's one-time setup

Run once per host, as the owner, from the root of the authority checkout. The first line needs no
sudo, the second is the one sudo command, the third and fourth need none.

Two values are yours to fill in before you run anything:

  C  the commit you approved, written as its full hash. Not a branch name and not a short form.
  H  the SHA-256 digest of that commit's build of the reader. Copy H from the review record you
     approved for C. Do not read it back from the checkout: not from what line 1 prints, and not
     from proof/VELDO-0344/reader.sha256 as the checkout shows it. A digest read from the place
     the source is read from would follow a substitution made there.

Line 1 builds the reader from the blob of commit C, not from the working tree, and prints the
digest of the build. It must print H. It reads the blob with git's cat-file under
--no-replace-objects, because git show follows replace refs and any process of your account can
add one:

d=$(mktemp -d) && g=$(id -gn) && /usr/bin/git --no-replace-objects cat-file blob C:scripts/veldo_procread.c > "$d/veldo_procread.c" && (cd "$d" && env -i PATH=/usr/bin:/bin /usr/bin/cc -std=c11 -O2 -Wall -Wextra -Werror -static -ffile-prefix-map="$d"=. -o "$d/veldo-procread" veldo_procread.c) && sha256sum "$d/veldo-procread"

Line 2 is the sudo command, in the same shell, with H written into it. Root opens no path your
account controls: your own shell opens the build and hands it to root as standard input. Root
copies it into a temporary file of its own, compares that copy with H, and only then sets the
owner, the mode and the capability and moves the file into place:

sudo sh -c "umask 077 && { [ -d /usr/local/lib/veldo ] || { mkdir -p /usr/local/lib/veldo && chmod 0755 /usr/local/lib/veldo; }; } && t=\$(mktemp /usr/local/lib/veldo/.veldo-procread.XXXXXX) && if cat > \"\$t\" && echo 'H  '\"\$t\" | sha256sum -c - >/dev/null; then chown root:'$g' \"\$t\" && chmod 0750 \"\$t\" && setcap cap_sys_ptrace=ep \"\$t\" && mv -f \"\$t\" /usr/local/lib/veldo/veldo-procread || { rm -f \"\$t\"; echo 'the install failed: nothing installed' >&2; exit 1; }; else rm -f \"\$t\"; echo 'digest differs: nothing installed' >&2; exit 1; fi" < "$d/veldo-procread" && rm -r "$d"

Line 3 installs the two user units and starts the socket. Then write H into the installation's
space section as process_reader (a string of 64 hexadecimal digits), and run line 4, the reader
check:

python3 -I .veldo/control_space_probe.py reader-units && systemctl --user daemon-reload && systemctl --user enable --now veldo-procread.socket
python3 -I .veldo/control_space_probe.py reader

What it does, in order:
1. Reads scripts/veldo_procread.c as commit C holds it and builds it statically and reproducibly
   in a temporary directory, with the compiler at /usr/bin/cc and an empty environment.
2. Your shell, with your permissions, opens the build and gives it to the sudo command as its
   standard input. Root reads that input and never a path in your temporary directory, so a link
   put there by a process of your account gives root nothing you could not read yourself. Root
   writes the copy into a temporary file of its own in /usr/local/lib/veldo, under umask 077:
   owner root, mode 0600. The folder is made with mode 0755 only when it is not there yet; one
   that exists is left as it is.
3. Compares that copy with H. When they differ, root removes the copy and the line ends with
   "digest differs: nothing installed", whatever a process of your account did to the compiler,
   the source, the checkout's refs or the built file. Nothing is left behind, and a reader
   installed earlier is not touched.
4. Only after the comparison: sets owner root, group your own group, mode 0750, so that your
   account can run it and no other account can; then the one file capability,
   cap_sys_ptrace=ep, after the change of owner because a change of owner clears it; then moves
   the file to /usr/local/lib/veldo/veldo-procread. The file is in place only once it holds the
   capability. When one of these steps fails, root removes the copy and the line ends with "the
   install failed: nothing installed".
5. Writes veldo-procread.socket and veldo-procread@.service into your systemd user unit
   directory and starts the socket. They are user units: no sudo, no system service, no second
   account. The service unit carries no NoNewPrivileges and no sandboxing setting, because the
   kernel grants a file capability only without them; the reader locks itself in after it has
   been executed. The authority unit is not changed and never holds the capability.
6. Runs the reader check, which reads through the socket as every probe does. It prints the
   reader's state and one PASS or FAIL line for each of its six rows. It must print "state used
   cap=1" and six PASS lines, and it exits 0 only then: the state is used; it read an undumpable
   process it started itself, whose second thread sits in another folder (three rows, all of
   your own uid); process 1, which is root's and which the probe cannot read itself, has a
   whole block in the reader's table, with the start time the probe reads; and the run label of
   that undumpable process, whose environment the probe is refused, is read and is the one the
   check started it with, and the label of process 1 is read too. The fifth row is the one that
   shows the capability reading a process of another uid. The sixth shows the label being read.

What the reader is: a static program that reads entries of the process table and prints numbers,
the device and inode numbers of each process's working directories, open files and mapped files,
and one more thing: the run label. A wrapped run gives its command one environment variable,
VELDO_SPACE_LABEL, whose value names the run. For each task the reader reads the environment and
prints the value of that one variable, in hexadecimal, or that there is none. It prints no other
variable, no name and nothing else of an environment, and it keeps no log. It takes no input,
attaches to no process, signals none and writes nothing but that table. An agent running as you
can connect to the socket and learn those numbers, and which run each process says it belongs
to, for every process on the host; it learns no path, no file name, no content, no memory and
no other variable of any environment.

Without the reader, or with one that fails a check, nothing is removed that would have stayed:
every process the probe cannot read is judged as before, and the probe's answer names the
reader's state (absent, or refused with the check that failed).

What a change costs. An upgrade of the compiler or of the C library changes nothing that is
installed. It changes what line 1 prints on this host, so a new install waits until a gate run on
that compiler has recorded the new digest and you have approved it. An edit of the reader's
source leaves the installed binary working with its old pin. When the edit changes the output
format, the probe refuses the old binary's output, and every item under your home folder defers
until you have installed and pinned the new build.

Undo: any one of these three lines is enough to turn the reader off, and after it the probe
reports the reader as refused or absent. Then set process_reader to none.

systemctl --user disable --now veldo-procread.socket
sudo setcap -r /usr/local/lib/veldo/veldo-procread
sudo rm /usr/local/lib/veldo/veldo-procread

Uninstall: the full removal, from the root of the authority checkout. It can be undone by running
the setup again.

systemctl --user disable --now veldo-procread.socket
systemctl --user stop 'veldo-procread@*.service'
rm -f "${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/veldo-procread.socket" "${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/veldo-procread@.service"
systemctl --user daemon-reload
systemctl --user reset-failed 'veldo-procread*'
sudo rm -f /usr/local/lib/veldo/veldo-procread
sudo rmdir --ignore-fail-on-non-empty /usr/local/lib/veldo

Then set process_reader to none in the installation's space section, or remove the key. The
rmdir keeps the folder while anything else lives in it. After this the probe reports the reader
as absent and judges every process it cannot read as before.
