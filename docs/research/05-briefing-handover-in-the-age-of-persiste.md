# BRIEFING: Handover in the age of persistent AI memory + agents

## The thesis (and it holds up)

The classic handover artifact (a wiki page, a Confluence "onboarding" doc, a leaving-engineer's brain dump) is being replaced by three things that already live where the work happens: (1) **in-repo context files** the agent reads on every session (AGENTS.md / CLAUDE.md), (2) **docs moved into the repo** next to code (ADRs, RFCs, specs, architecture), and (3) **persistent AI memory** that accumulates the tacit "how we actually work" layer. The repo + context files + memory ARE the handover. A human or an agent reconstructs context by reading and querying, not by attending a meeting or reading a stale wiki. This is not speculative for you: your file-based memory + KB already IS the "enterprise memory layer" that vendors are now selling to big orgs to solve the "senior person resigns, three weeks of handover compressed into one" problem.

## Key findings

- **AGENTS.md is now the real standard, not a fad.** Released by OpenAI Aug 2025, transferred to the Linux Foundation's Agentic AI Foundation late 2025 (alongside MCP). By mid-2026: 28+ tools with native support, 60,000+ public repos carry one. It is plain Markdown, no required fields. The governing rule: "every line should contain information the agent cannot get from reading your code, package manifests, or existing docs."
- **The onboarding reframe is explicit in the literature.** These files are described repeatedly as "onboarding documentation for a team member who never retains institutional knowledge." The canonical anecdote: three months of correcting the same mistakes every session, fixed overnight by a 40-line context file. README = for humans; AGENTS.md = the extra build/test/convention context that would clutter a README.
- **Docs belong in the repo, and AI is the forcing function.** The argument ("it's never been that easy to keep them up to date"): co-location means one search hits code + docs, PRs review docs like code, examples run in CI, and the agent gets higher-level context (RFCs/PRDs/architecture) for free. Use Mermaid, not screenshots (searchable, diffable). "80% of the rules file could have been documentation instead."
- **Spec-driven development (SDD) is the heavier cousin worth knowing.** The spec is the durable, version-controlled source of truth; code is a regenerable output. Emerged in 2025 as the answer to vibe-coding drift. GitHub Spec Kit (88k stars, four commands: specify -> plan -> tasks -> implement) is the reference implementation. GitHub also shipped **Agentic Workflows** (Feb 2026): intent-driven repo automation authored in plain Markdown, run in Actions. Relevant because it points at where "tickets" are going: a short spec.md file is the ticket, the handover, and the agent brief in one.
- **Memory has a settled shape.** Four layers: CLAUDE.md (static, hand-authored, every session), MEMORY.md (auto-learned "what Claude observed about how you work," first ~200 lines / 25KB auto-loads), the Memory tool (API retrieval for long agents), and per-subagent memory (frontmatter, v2.1.33+, so a reviewer agent builds durable expertise). Multi-session pattern: "assume interruption," commit progress logs incrementally, recover state from memory + git log rather than context window.

## Practices worth stealing (concrete)

1. **One AGENTS.md per repo, CLAUDE.md as a symlink to it.** You are polyglot (Django, Kotlin, PostGIS, Rust, CMS) and Dmitry uses multiple agent tools. Make AGENTS.md canonical and `ln -s AGENTS.md CLAUDE.md` so Claude Code, Codex, and Cursor all read one file. Portability solved, no drift between two files.
2. **Hard length ceiling and a deletion test.** Keep each under ~150 lines (HumanLayer runs under 60). Frontier models follow ~150-200 instructions reliably and Claude's system prompt already eats ~50, so every line is a tax. The filter: "would removing this line cause a mistake? If not, cut it."
3. **Progressive disclosure, not one giant file.** CLAUDE.md carries identity + exact build/test commands + guardrails, then lists pointers: `docs/deploy.md`, `docs/migrations.md`, `docs/architecture.md` with one-line descriptions so the agent loads them on demand. Prefer `file:line` pointers over pasted code (copies rot).
4. **Move docs into each repo, kill the DEV-project Confluence habit.** `docs/adr/`, `docs/rfc/`, `docs/specs/`. Author in-repo first; any external tracker is a mirror. The PR that changes behavior changes the doc in the same diff. This is your handover.
5. **Never auto-generate the context file.** Research cited across sources: LLM-authored instruction files underperform hand-authored ones. `/init` is a starting draft, not the artifact.
6. **Replace heavy tickets with in-repo specs for anything non-trivial.** A `spec.md` on the feature branch (what, why, success criteria, edge cases) does the job Jira feels too heavy for, and doubles as the agent brief. Reserve full Spec Kit ceremony for the Rust core and anything with real blast radius; use a lightweight one-file spec everywhere else.
7. **Treat memory + KB as Misha's onboarding.** When the new CS/dev hire lands, the first move is "query the memory and read the repo AGENTS.md files," not a handover call. Your MEMORY.md-style index (which you already run for Ava) is exactly the model: a keyword-indexed surface that points to detail files.
8. **Governance against drift is the only real risk.** Docs-in-repo wins only if PRs keep them fresh. Add a light CI check or a review invariant ("behavior change requires doc/spec update in the same PR"). This is the one place to spend process budget.

## What specifically applies to your tiny team

- You are already 80% there: the daybook CLAUDE.md + memory index + KB is the pattern the industry is converging on. The gap is that your **DEV repos** (companion, mobile, places, core, CMS) likely lack lean, hand-authored AGENTS.md files with exact commands and the "always do X / never do Y" guardrails. That is the highest-leverage next step and it costs an afternoon per repo.
- Because Dmitry and each dev own distinct repos (Igor=Django, Frontend=Kotlin, Infra=infra, Docs-eng=docs), per-repo AGENTS.md is also **implicit ownership + handover**: if Igor is out, Dmitry's agent still ships in the Django repo because the context is in the repo, not in Igor's head.
- Skills vs context files: keep repo-specific facts in AGENTS.md; capture **cross-repo procedural workflows** (how we cut a release, how we write a migration, how we deploy the companion with the bind-mount gotcha) as reusable skills. Your existing playbooks/*.yaml are already this.
- Do NOT buy an enterprise memory-layer SaaS (Glean/Guru/Coworker). Those exist to bolt memory onto orgs that never had repo-native context. For five people the repo + file memory IS the layer, and adding a vendor is exactly the heavy process you are avoiding.
- Skip full Spec Kit as a mandate. Its four-command ceremony is right for the Rust telecom core (high correctness bar) and overkill for a CMS tweak. Adopt the idea (spec is durable, code is regenerable), not the whole CLI, everywhere else.
