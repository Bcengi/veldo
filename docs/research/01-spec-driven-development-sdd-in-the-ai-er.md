# Spec-Driven Development (SDD) in the AI era: briefing for a tiny Claude Code team

## The thesis (what this actually is)
SDD makes a versioned, structured spec the source of truth, and treats code as a disposable expression of that spec generated and re-generated by an agent. It is the industry's structured answer to "vibe coding" failing at scale: agents produce plausible code that drifts from intent, hallucinates APIs, and decays. Spec Kit's own doc states it bluntly: "The specification becomes the primary artifact. Code becomes its expression in a particular language and framework." Maintenance becomes "evolving the spec," not patching code and back-filling docs. The universal flow is the same across every tool: **Spec -> Plan -> Tasks -> Implement**, each phase a reviewable Markdown artifact that feeds the next, with a human approval gate between phases.

## The three canonical flavors, compressed

**GitHub Spec Kit** (open source, agent-agnostic, works with Claude Code). Slash commands drive it: `/speckit.constitution` (project's non-negotiable principles), `/speckit.specify` (the what and why, no tech stack), `/speckit.plan` (technical plan + `data-model.md` + `contracts/` + `research.md`), `/speckit.tasks` (dependency-ordered list, parallelizable items marked `[P]`), `/speckit.implement`. Files live in-repo: `specs/[branch-name]/{spec.md,plan.md,tasks.md,...}` plus `memory/constitution.md`. Human writes the vague idea, resolves items the agent flags `[NEEDS CLARIFICATION]`, and approves at each gate; agent does clarifying dialogue, technical translation, and constitution-compliance checks. This is "the reference implementation everyone benchmarks against."

**AWS Kiro** (agentic IDE, Code-OSS fork, launched July 2025). Three artifacts per feature: `requirements.md` (user stories + EARS acceptance criteria), `design.md` (architecture, sequence diagrams, data flow), `tasks.md` (discrete trackable tasks). Two distinctive mechanisms worth knowing: **steering files** in `.kiro/steering/*.md` (persistent project conventions: logging, security, testing standards, injected into every interaction) and **agent hooks** (event-driven automation on file save/create: regenerate tests, refresh docs, run security scans). Kiro also builds a task dependency graph and runs independent tasks concurrently in "waves." The cost is IDE lock-in and heaviness.

**OpenSpec** (Fission-AI, git-native, lightweight, built for brownfield). Rejects databases: pure Markdown in the repo, specs live beside source in version control as living documentation. Flow: `/opsx:explore -> propose -> apply -> verify -> archive`. Its novel unit is the **change proposal** with **spec deltas**: instead of rewriting a giant spec, you describe a change and it generates a proposal, tasks, design decisions, and a diff showing how requirements change; completed changes get archived for reference. Works with 30+ tools including Claude Code. This is the closest fit to a small fast-moving team.

## The EARS trick (steal this regardless of tool)
Kiro popularized EARS (Easy Approach to Requirements Syntax) for acceptance criteria: **WHEN [condition] THE SYSTEM SHALL [behavior]**. Example: "WHEN a user submits a valid email THE system SHALL send a one-time login link valid for 15 minutes." It is one line, testable, unambiguous, and it maps one-to-one onto a test. Ban vague words ("appropriate," "reasonable," "user-friendly"); require measurable criteria and explicit error paths, not just the happy path. This is the single highest-leverage habit here and it costs nothing to adopt.

## Concrete practices worth stealing
- **Specs live in the repo, one feature per directory** (`specs/NNN-feature-name/`), 1 to 3 pages max. Co-location keeps them in the CI loop and out of a wiki where they become "archaeology."
- **Never jump spec -> code. Review the plan, then review the tasks.** The gate between phases is where the value is; the thinking phase is what you are actually reviewing, not the diff.
- **Aim for "spec-anchored," not "spec-as-source."** The 2026 consensus sweet spot: specs and code evolve together, and automated tests enforce alignment. You do not literally regenerate the whole codebase from spec (that "spec-as-source" purity is where SDD "collapses"). Tests are the anti-staleness mechanism.
- **Cite the spec in commits** for free traceability: `feat(auth): magic link, refs specs/004-magic-link/spec.md`. This replaces most of what a ticket tracker gives you.
- **A "constitution" / steering layer** of durable, cross-feature rules (conventions, banned patterns, architecture principles) separate from per-feature specs.
- **Split the session by model/job**: heavier reasoning model for spec authoring, cheaper fast model for implementation. Different jobs, different sessions, disciplined context resets.

## What specifically applies to Bcengi (opinionated)

You are exactly the team the pundits say should NOT adopt heavyweight SDD (solo/small, ships fast, changing requirements). So do not install Kiro and do not adopt full Spec Kit ceremony. But three things fit you unusually well:

1. **Specs-in-repo can replace the heavy Jira DEV project for anything non-trivial.** Your complaint that DEV "feels too heavy" is the exact pain SDD solves from the other direction: the spec IS the ticket, it lives next to the code it describes, the agent reads it directly, and the commit references it. Keep Jira CEO for business/strategy; for engineering, a `specs/NNN-*/` directory per feature per repo plus commit refs gives you traceability without the ticket overhead. This is a cleaner fit than forcing DEV tickets to carry detail.

2. **You already have the "constitution" and the memory layer, so your marginal cost is near zero.** Your per-repo `CLAUDE.md` files plus file-based memory and KB already function as steering files. SDD just adds the missing middle layer: the durable rules exist (CLAUDE.md), the conversation history exists (memory), but the per-feature intent artifact is currently ephemeral in a chat. Writing it to `specs/` is the small delta. Your persistent memory changes what "handover" means: the handover is not a ticket description or a Slack thread, it is `spec.md` + `tasks.md` in the repo that the next Claude Code session (or the next dev) reads cold and continues. That directly serves your distributed-team, async-handover reality (Frontend/Igor/Infra/Docs-eng each pick up a repo's spec without a meeting).

3. **OpenSpec's change-proposal + spec-delta model is the right pattern for you, because everything you build is brownfield.** You are not greenfielding; you are evolving a Django companion, a Kotlin app, a PostGIS dataset, a Rust core. OpenSpec was built specifically for "describe a change to an existing codebase, get a proposal + tasks + a diff of how requirements change," with an archive of past changes. That maps to how you actually work far better than Spec Kit's greenfield feature-numbering. And it is git-native Markdown with Claude Code slash commands, so it adds a thin process, not an IDE or a server.

**The recommendation:** adopt "spec-anchored lite." For any change bigger than a bug fix or a quick exploration, have Claude Code write a 1-page `spec.md` with EARS acceptance criteria and a `tasks.md` into `specs/NNN-name/` in that repo, gate on you reviewing plan-then-tasks, cite the spec in the commit, and let tests enforce alignment. Use OpenSpec's proposal/delta framing as the mental model. Skip constitutions-as-new-files (your CLAUDE.md already is one). This costs one extra reviewable artifact per feature and buys you agent-legible intent, real async handover, and Jira relief, with zero new infrastructure and no army to run it.

**This also aligns with your RULE #6 (right architecture, no shortcuts):** a reviewed spec + plan gate is the structural place to catch "the agent picked a reasonable default that is actually a shortcut" before it becomes code you have to unwind.

## Traps to avoid
- Do not go "spec-as-source" purist (regenerate-everything). That is the flavor critics say "will collapse" and it is waterfall reborn. Stay spec-anchored.
- Do not spec bug fixes or exploratory spikes. The quoted line: specforcing a bug fix is "like filing a building permit to hang a picture frame." Vibe-code exploration, spec the things you will maintain.
- Do not let specs sprawl past ~3 pages or move them to Confluence/wiki. In-repo and short, or they rot.
- Do not adopt hooks/multi-agent orchestration on day one. Spec file + plan-mode review + disciplined `/clear` is ~80% of the value; the rest is optimization once the habit is muscle memory.
