# Briefing: Anthropic's Claude Code methodology, and what a tiny team should steal

## The one-sentence thesis
Anthropic's whole methodology reduces to a single constraint plus a single habit. The constraint: **the context window is the scarce resource, and model quality degrades as it fills**. The habit: **give Claude a machine-checkable way to verify its own work** so a human is not the verification loop. Everything else (CLAUDE.md hygiene, plan-then-code, subagents, worktrees, spec files) exists to serve those two things. If Bcengi adopts only two things, make them: aggressive context discipline and a verify-loop per repo.

## Key findings (what Anthropic actually recommends)

**1. Verification is the highest-leverage practice, full stop.** The official docs and the power-user guide both say it outright: "The single most impactful tip is verification." Claude stops when work "looks done"; without a check it can run, the human becomes the loop and every mistake waits to be noticed. Give it a pass/fail signal (test suite, build exit code, linter, a script that diffs output against a fixture, a browser screenshot compared to a design) and the loop closes itself. Escalation ladder, cheap to strict: verify-in-one-prompt -> a `/goal` condition re-checked every turn -> a `Stop` hook that blocks the turn from ending until a script passes (Claude Code force-ends after 8 consecutive blocks) -> an adversarial reviewer subagent in fresh context. Source: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices), [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips).

**2. Explore -> plan -> implement -> commit, as distinct phases.** Plan mode (Shift+Tab to cycle in; Ctrl+G to open the plan in your editor and hand-edit before execution) separates research from execution so Claude does not confidently solve the wrong problem. But they are explicit that planning has overhead: **"If you could describe the diff in one sentence, skip the plan."** Plan only when the approach is uncertain, the change spans multiple files, or the code is unfamiliar. Power-user framing: "Pour your effort into the plan so Claude can one-shot the implementation." Source: [Best practices](https://code.claude.com/docs/en/best-practices).

**3. Spec-driven, with a clean-context handoff.** For larger features, have Claude interview YOU first (the `AskUserQuestion` tool), write a self-contained `SPEC.md` that names the files/interfaces involved, states what is out of scope, and ends with an end-to-end verification step, then **start a fresh session to execute it**. The spec is the handoff artifact; the implementing session gets clean context. Anthropic's own teams "plan in a normal chat (claude.ai), then move the structured prompt into Claude Code." Source: [Best practices](https://code.claude.com/docs/en/best-practices), [How Anthropic teams use Claude Code (PDF)](https://www-cdn.anthropic.com/58284b19e702b49db9302d5b6f135ad8871e7658.pdf).

**4. CLAUDE.md is a liability if it is long.** The failure mode is named explicitly: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." Litmus test per line: "Would removing this cause Claude to make mistakes? If not, cut it." The steering blog puts a number on it: **keep CLAUDE.md under ~200 lines with an owner.** Include only what Claude cannot infer from code (non-guessable bash commands, style rules that differ from defaults, test runner, repo etiquette, project-specific architecture decisions, env quirks, non-obvious gotchas). Exclude anything Claude can read from the code, standard conventions, and detailed API docs (link instead). `IMPORTANT`/`YOU MUST` raises adherence. Source: [Best practices](https://code.claude.com/docs/en/best-practices), [Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more).

**5. There is now a clean division of labor between the customization mechanisms.** This is the most useful conceptual model for a team, from the steering blog:
- **CLAUDE.md** = always-loaded project facts and conventions. Persistent, costs context every session.
- **Skills** (`.claude/skills/<name>/SKILL.md`) = procedural, sometimes-relevant workflows (deploy steps, release checklist, review process). Loaded on demand, near-zero idle context cost. **This is where most of what people wrongly stuff into CLAUDE.md belongs.**
- **Subagents** (`.claude/agents/*.md`) = isolated side tasks with their own context and tool allowlist; return only a summary. For noisy work (deep codebase search, log analysis, dependency audit, security/code review) that would otherwise pollute the main context.
- **Hooks** (`.claude/settings.json`) = deterministic, non-negotiable enforcement at lifecycle events. "Advisory" CLAUDE.md rules vs "guaranteed" hooks. If a rule MUST happen every time (run linter after edit, block writes to a protected dir, run the test gate before a turn ends), it is a hook, not a CLAUDE.md sentence.

Decision rule worth memorizing: procedural -> skill; must-happen-every-time -> hook; noisy/isolated -> subagent; always-true facts -> CLAUDE.md. Source: [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more).

**6. Context management is a discipline, not an afterthought.** `/clear` between unrelated tasks. Hard rule: **after two failed corrections on the same issue, `/clear` and rewrite the prompt** with what you learned, because the context is now polluted with failed approaches and a clean session almost always beats a long one. `/compact <instructions>` for targeted compaction; `/rewind` (or Esc+Esc) for checkpoint restore of conversation and/or code; `/btw` for a side question that never enters history. Named anti-patterns: "the kitchen sink session," "correcting over and over," "the over-specified CLAUDE.md," "the trust-then-verify gap," "the infinite exploration." Source: [Best practices](https://code.claude.com/docs/en/best-practices).

**7. Long-running / unattended runs get a specific harness.** Anthropic's engineering post on long-running agents describes a two-agent structure (an initializer that sets up the environment once, then a coding agent that makes incremental progress) plus persistent on-disk state artifacts: a **feature-list JSON with per-feature `passing: true/false` status** (agent may not mark passing until verified, may not delete tests to make things "pass"), a **`claude-progress.txt`**, descriptive git commits as a progress log, and an **`init.sh`** to reliably restart dev servers. Rule: **work one feature at a time** (the dominant failure mode is trying to do too much at once and leaving things half-built), and **test end-to-end as a user would** (browser automation), not just unit tests. Source: [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).

**8. Parallelism is the scaling story for small teams.** Power users and Anthropic both push git worktrees: run 3-5 (power users report 4-8) Claude sessions in parallel, each in an isolated worktree so edits do not collide (`claude --worktree`). Subagents can also run `isolation: worktree` for batched fan-out changes. For true batch (migrate 2,000 files), loop `claude -p "..." --allowedTools "Edit,Bash(git commit *)"` in a shell script, test on 2-3 files first, then run at scale. Writer/Reviewer pattern: one session implements, a SECOND fresh session reviews (fresh context is less biased toward code it just wrote). Source: [Best practices](https://code.claude.com/docs/en/best-practices), [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips), [Claude Code Worktrees Guide (2026)](https://www.claudedirectory.org/blog/claude-code-worktrees-guide).

**9. CLAUDE.md vs AGENTS.md, current state (spring 2026).** AGENTS.md is now the cross-tool standard (OpenAI-originated Aug 2025, moved to the Linux Foundation's Agentic AI Foundation, read by 30+ tools, 60,000+ repos). Claude Code does NOT natively parse AGENTS.md when a CLAUDE.md exists; it reads CLAUDE.md as its richer native format (it alone supports `@imports`, path-scoped rules, and hierarchical user/project/local memory). As of spring 2026 Claude Code will read AGENTS.md **only when no CLAUDE.md is present**. Recommended pattern if you ever run multiple agent CLIs: put shared instructions in `AGENTS.md`, make CLAUDE.md a one-line `@AGENTS.md` import (or symlink), keep Claude-specific config in CLAUDE.md. Source: [CLAUDE.md vs AGENTS.md in 2026 (bestagent.dev)](https://bestagent.dev/claude-md-vs-agents-md-2026/), [AGENTS.md Spec 2026 (morphllm)](https://www.morphllm.com/agents-md-guide).

## Concrete practices worth stealing (opinionated shortlist)

1. **A per-repo verify gate, wired as a `Stop` hook.** For each Bcengi repo the gate is different and that is the point: Django companion = pytest + the real e2e path (drive the live bot via POST /api/v1/chat/, per your existing testing rule); Kotlin mobile = `./gradlew :app:assembleDebug -x lint` plus on-device check; PostGIS places = the query-budget check (nothing >500ms) plus a fixture diff; Rust core = `cargo test`/build. Encode each as a script the Stop hook runs so "done" means "the gate passed," not "looks done." This is the single change with the highest payoff and it directly operationalizes your existing self-test-before-showing rule.

2. **Move 80% of your CLAUDE.md into skills.** Your project CLAUDE.md plus MEMORY.md is enormous. Anthropic's own guidance says a bloated always-loaded file makes Claude ignore rules. Your Tier-0 hard gates (no em-dashes, spend gate, public-vs-private metrics, PRICES hands-off, right-architecture) belong in CLAUDE.md because they are always-true. But procedural playbooks (`spend_decision_review.yaml`, `daily_reports.yaml`, `social_post_creation.yaml`, `contract_drafting.yaml`) are exactly what the steering blog says should be **skills**, loaded on keyword match, not paid for on every turn. You already have the trigger-keyword index; converting those to `.claude/skills/*/SKILL.md` with `description:` frontmatter is a near-mechanical migration and would cut idle context materially.

3. **`SPEC.md` per feature as the real handover unit.** For a distributed team where Frontend, Igor, Infra, and Docs-eng each drive Claude Code, the durable artifact is not a Jira ticket, it is a self-contained spec committed to the repo (names the files, states out-of-scope, ends with the e2e verify step). Anyone (or any fresh Claude session) can pick it up. This is the answer to "Jira DEV feels too heavy": the spec lives in git next to the code, and Jira holds only the one-line "what and why," not the implementation detail.

4. **The feature-list JSON + `claude-progress.txt` pattern for multi-session builds.** Your bigger workstreams (CoreConnect production deploy, companion round-2, module_system) are long-running and cross-session. Adopt Anthropic's long-agent artifacts: a checked-in feature list with `passing:` flags and a progress file. This is a better cross-session handoff than a heavy tracker and plugs straight into your existing file-based memory habit.

5. **Adversarial review as a subagent, not a person.** Run the bundled `/code-review` skill (fresh subagent, sees only the diff) before merge, and `/simplify` after changes (parallel agents check reuse, quality, efficiency, and CLAUDE.md compliance in one pass). For a team with no QA army, this is your QA. Tell the reviewer to flag only correctness/requirement gaps, because a reviewer asked for gaps will invent them and lead to over-engineering (Anthropic warns about this explicitly).

6. **Worktrees, checked into your team norms.** With a 5-person team building across many repos, `claude --worktree` per parallel task and pre-approved safe commands in a checked-in `.claude/settings.json` is how you get "20-dev output from 5 devs" without collisions. This matches your existing parallel-agent-fleet rule.

## What specifically applies to Bcengi (and what does NOT)

**Applies directly:**
- Your **file-based memory + KB changes what "handover" means** exactly the way Anthropic's on-disk state artifacts (progress files, feature lists, specs) do. You are already doing the durable-artifact thing; formalize it as `SPEC.md` + feature-list JSON in each repo and you have a handover model that needs no ceremony.
- "**No heavy process, no army**" is Anthropic's own posture: the docs push automation (hooks, skills, subagents, worktrees, `-p` fan-out) precisely so you do not add people. The methodology is process-light and tooling-heavy.
- Dmitry being highly technical and hands-on is the ideal profile: the docs assume the human is oversight and course-corrector (Esc early, `/rewind`, two-correction rule), not a typist.

**Does NOT apply / avoid:**
- Do not treat Jira DEV as the coordination layer for implementation detail. Anthropic's teams coordinate through **committed artifacts and clean-context handoffs**, not tickets. Keep Jira for the "what/why/priority" ledger (which your CEO board already is) and push implementation state into git-resident specs and progress files.
- Do not let the giant CLAUDE.md keep growing. It is currently working against adherence per Anthropic's stated failure mode; the fix is skills-migration and ruthless pruning, tested by watching whether behavior actually shifts.
- Do not add "agent teams" orchestration or dynamic workflows yet. Those are for large autonomous fan-out; a 5-person team gets 90% of the value from verify-gates + worktrees + skills.
