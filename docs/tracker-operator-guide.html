Working with Veldo and Your Tracker

The operator companion to the tracker integration: how a person files work from Jira or Confluence, what to put on the ticket, and what happens to it after. If the Plugin Guide section 12 tells you what the tracker bridge IS, this tells you how to WORK with it, day to day.

Who this is for#

You live in a tracker. You open a Jira ticket, you write a Confluence requirements page, and you want the engineering to happen and the ticket to stay honest without you babysitting it. This guide is written for you, not for the person wiring the plumbing. You do not need to open the repository, run a command, or learn the spec format. You flag a ticket, you type a few sentences when asked, and the rest is mechanical.

The shape in one paragraph: you put a routing signal on a ticket or page (a label that names the target repository), someone runs intake, and Veldo drafts a specification in the right repository from your ticket. From there the ordinary Veldo loop builds and proves the change. As it moves, a one-way mirror writes progress back onto your ticket in your own tracker statuses, and posts a closing note when it ships. You never hand-update the ticket, and you never guess where a change is: the ticket tells you.

What "wired" means before you start#

The bridge is off until a repository (or the organization that owns several repositories) turns it on. That setup is a one-time job done in the repository, not something you do per ticket, but it helps to know what has to be true for your ticket to be picked up:

  • A per-org config, .veldo/trackers.json. It declares the routing rule (how a ticket names its repository) and the status_map (how each Veldo status maps onto your tracker's own column names). A ready-to-edit template ships at plugin/templates/.veldo/trackers.json.
  • The target repository on the spec, an optional tracker_repo field. Because one tracker project spans many repositories, a spec (and a plan) can carry an optional tracker_repo front-matter field naming which repository the work targets when it is mirrored. Intake sets it for you from your routing signal, so you never type it; when it is absent Veldo treats the work as single-repository. If a tracker config is wired, the value must name a known repository or the repository's own contract check fails closed, so a mirror target nobody can resolve is caught early.
  • Auth by reference. The live connection to Jira or Confluence is plain, non-LLM Python that runs unattended and deterministically. It authenticates with a token REFERENCE, token_ref (for example env:JIRA_TOKEN), which points at your secrets store. A raw credential never appears in a config file, a prompt, a proof, or a log, and the connection fails closed if no token resolves.
  • Honesty about what is live. The routing, mapping, intake, and mirror LOGIC is mechanical: it is enforced in code and gate-tested offline against an in-memory fake tracker, so its behavior is proven. The live Jira Cloud and Confluence Cloud connections are shipped REFERENCE implementations that a repository wires to its own instance. The round-trip described below is real once that live adapter is wired to your instance; do not assume a live instance is connected the moment you install the plugin.

You do not have to read .veldo/trackers.json to use the bridge. If your work is not being picked up, that config, and whether the live adapter has been wired, is the first thing for whoever set it up to check.

Getting work IN: intake#

Intake is how a ticket or a page becomes a Veldo specification. You do two things: put a routing signal on the item, and ask for intake.

1. Flag the item with a routing signal#

Veldo has to know which repository your work targets, because one tracker project commonly spans many repositories. You say so with a routing signal. The default and simplest mechanism is a LABEL:

veldo-repo:web-app

That label, on a Jira ticket, routes it to the repository whose id is web-app. The label prefix (veldo-repo:) is set in .veldo/trackers.json; a stock Jira project with no custom fields works out of the box. Two other mechanisms exist if your org prefers them: a Jira COMPONENT whose name matches a repository id, or a dedicated named FIELD. Whoever wired the tracker picks one; you use whichever they chose.

For a Jira bug or task, that is all the structure you need: the label plus the normal summary and description you already write.

For a Confluence requirement, copy the shipped requirements template (plugin/templates/confluence-requirements-template.md) into a page, add the same veldo-repo:<repo> label to the page, and fill in its two load-bearing sections:

  • Outcomes - what becomes true for a user or the business when this ships, one bullet each.
  • Acceptance Criteria - observable, checkable statements that must hold, one bullet each. These become the draft spec's acceptance criteria.
  • Open Decisions (optional) - any product question still open; intake surfaces these to the owner rather than guessing.

2. Run intake#

Someone runs the /veldo:intake skill, pointing it at your item (the ticket key or the page). You do not run it yourself unless you also work in the repository; it is the one step that crosses from the tracker into the repo.

3. What you get back#

Intake reads your item through the vendor-neutral connection, resolves the target repository from your routing signal, and drafts a veldo.spec/v1 specification bound to that repository:

  • For a bug, the first acceptance criterion (AC1) is the REPRODUCTION: intake reproduces the bug and writes it as a failing test, recording that it fails on the current code. A no-regression criterion is added as the last AC.
  • For a requirements page, the acceptance criteria come FROM your page, renumbered AC1..ACn, plus the same no-regression criterion.
  • Either way, your source item is linked in the draft's intake_source field, and its content is treated as data, never as instructions (it is sanitized against injection).

The draft is exactly that, a DRAFT. A human owner completes it (answers any single product question intake raised, tightens the criteria) and marks it ready. From ready onward it is an ordinary Veldo change.

It refuses rather than guess#

Intake FAILS CLOSED, by name, when the routing signal is missing, names an unknown repository, or is ambiguous (names more than one). It does not fall back to a default repository and it does not guess. This is deliberate: a change filed against the wrong repository is a silent mistake nobody decided to make. If intake refuses, the fix is on the ticket: add the label, correct the repository id, or remove the extra one, then run intake again.

Getting work in WITHOUT running intake: the autonomous loop#

The intake above is the manual path: someone runs /veldo:intake on your item. When the inbound bridge is turned on, you do not need anyone to run it. You assign the ticket to a shared robot user and move it through your own board, and the work drafts itself, waits for you to approve it, builds, and comes back updated. This is the loop the fleet is built for, and it is the same three moves every time.

The three moves you make in Jira#

  1. Tag the repository. Same routing signal as intake: a veldo-repo:<repo> label (or, if your org wired it that way, a validated "Veldo Repo" dropdown field). This says which repository the ticket targets.
  2. Assign it to the Agent user. There is a SINGLE shared robot account for the whole fleet, named in .veldo/trackers.json (the agent field). Assigning a ticket to that account is how you hand it to Veldo. Assign it to a person and Veldo leaves it alone; a ticket is only ever the fleet's to take when it is assigned to the Agent user.
  3. Move it to your ready-for-dev status. When the ticket is genuinely ready to build, move it into the status your board uses for that (out of the box, "Approved for dev"; your org can configure the set in ready_statuses).

Those three together are the ELIGIBILITY TRIPLE, and all three must hold at once: assigned to the Agent user AND in a ready-for-dev status AND tagged to a repository Veldo can resolve. Drop any one - a ticket assigned to a teammate, sitting in "Backlog", or tagged to a repository nobody recognizes - and the fleet never picks it up. The check fails closed and never guesses a repository.

What happens between the draft and the build#

The bridge does not wait for all three before it starts drafting. As soon as a ticket is assigned to the Agent user and its repository resolves, the bridge drafts the spec (running the same intake described above) and posts that draft back onto the ticket as a comment, so you can read the ACTUAL specification it wrote. That is stage one, and it is all it does at that point: the draft is not claimable, and nothing builds yet.

Stage two is YOUR approval, and it happens entirely in Jira. When you move the ticket into the ready-for-dev status (with it still assigned to the Agent user), you are approving that drafted spec. Only then does Veldo promote the draft to ready and let a fleet worker claim it. Nothing the machine drafts approves itself; the promote is your action on the board. If you change your mind, reassign the ticket off the Agent user or move it back out of the ready status, and it will not build.

Because both the drafting and the promotion are reconcilers, re-seeing the same ticket is safe: Veldo never drafts a second spec, never posts the draft comment twice, and never promotes something you did not just approve.

What happens to the ticket AFTER: the round-trip#

This is the part people worry about: once the work is in the repo, do I have to track it myself and copy status back onto my ticket? No. You do nothing. The mirror does it.

You do not hand-update the ticket#

A one-way MIRROR projects the repository's truth back onto your tracker. It is driven by the events the Veldo loop already emits as the spec moves through its life, so it needs no separate bookkeeping from you and it NEVER polls your tracker. As the specification advances, Veldo transitions your ticket's issue to the matching status and, when the change ships, posts a closing comment:

The spec reaches Veldo status Your ticket moves to
marked readyreadyyour "ready" column
blocked on a questionblockedyour "blocked" column
a review verdict recordedin_reviewyour "in review" column (plus artifact links, and the ticket reassigned to your reviewer - see below)
shippedshippedyour "done" column (plus a closing comment)
mergedmergedyour "done" column

Your own tracker statuses, via the status_map#

Veldo does not impose its vocabulary on your board. Each Veldo status is translated to YOUR project's own column name through the status_map in .veldo/trackers.json. A small one looks like this:

"status_map": {
  "ready": "To Do",
  "blocked": "Blocked",
  "in_review": "In Review",
  "shipped": "Done",
  "merged": "Done"
}

So when the spec is marked ready, the mirror moves your ticket to "To Do"; when it ships, to "Done" with a closing comment. If your board has no column for a given Veldo status (many stock projects have no "in review" column), that status is recorded as a COMMENT instead of an invented transition, so the mirror never forces your ticket into a state your workflow does not have. Omit the status_map entirely and the mirror is comment-only.

At ready-to-test, the ticket hands off to your reviewer#

When the build is done and a review verdict is recorded, the ticket is at ready-to-test, and two things happen on it at once. The mirror posts a comment with the ARTIFACT LINKS that actually exist - the commit always, and the pull request and the proof when there is one - so you can go straight to the change without hunting for it (it never fabricates a link that does not exist). And it REASSIGNS the ticket away from the Agent user to your reviewer, so the ticket lands in a human's queue for testing rather than sitting on the robot account.

Who the reviewer is comes from .veldo/trackers.json: a per-repo reviewer overrides a global reviewer, and if neither is set the ticket goes back to whoever reported it. If none of those is known, the mirror leaves the assignee alone rather than invent one. This reassignment happens only at ready-to-test; while the work is being built the ticket stays on the Agent user, so you always know what is still in flight.

A plan builds an epic and children#

A single ticket becomes a single spec and a single child issue. A larger effort planned as a Veldo product plan mirrors its whole work graph onto your tracker as an EPIC with CHILD issues: the epic is keyed to the plan (one plan, one epic, never forked), and every work item becomes a child, so the entire structure is visible on your board even for items not yet started. Each child's status follows its work item's spec status through the same status_map; the epic rolls up to "done" once every work item has shipped, and stays open until then.

You can also start a whole plan from a REQUIREMENTS PAGE. If your Confluence requirements page carries a Deliverables work-breakdown section (the template has an optional one), a kickoff ticket that points at it drafts a Veldo plan rather than a single spec: the plan's outcomes come from the page's Outcomes, and it gets one work item per named Deliverable, all bound to the repository your veldo-repo:<repo> label resolves to. Like every other draft, the plan is a DRAFT a human refines and approves; the machine never approves its own plan. Once approved, the epic and its child issues are created on your board as described above, and each child becomes an approvable ticket that flows through the same loop - draft, your approval, build, round-trip.

It is one-way, and the repository wins#

Two rules keep this honest and worth stating plainly:

  • The mirror only ever writes status and comments. It never writes a spec or a plan definition back from the tracker. The repository stays the single source of truth. If your ticket and the repository ever disagree, the repository is right. Nothing you type in a ticket comment becomes engineering truth; a decision that changes a requirement is committed to the spec, not left in a comment.
  • It is idempotent and never polls. The mirror is a reconciler: it recomputes the desired ticket state from the repository each run and applies it. Replaying the whole event stream, or a doubled event, records no duplicate transition and no duplicate comment. It reads the repository's event stream, never your tracker.

If a spec is not wired for mirroring (no target repository set, no tracker config, an unroutable repository, or a spec that belongs to no plan for the epic path), the mirror simply SKIPS it by name. It does not error and it does not partially update your ticket.

How the mirror reaches your live tracker#

For the status changes, comments, links, and reassignment to actually appear in your Jira, someone on the repository side runs the mirror against your instance. That is a small, non-LLM runner (veldo mirror) that reads the repository's event stream and applies the desired ticket state through the live adapter. It is OPT-IN and OFF BY DEFAULT: installing Veldo starts no background service, sets up no timer, and spawns nothing on its own. Each run is one pass; whoever operates the repository decides how often to run it (a poll interval is just how often they run it again). Nothing about this is something you do from the tracker - it is set up once on the repository side, alongside the inbound bridge - but it is why the round-trip is real only after your team has turned these two services on against your instance, not the moment the plugin is installed.

The two-identity model: why the automation cannot approve its own work#

The autonomous loop rests on one structural guarantee: the automation must not be able to APPROVE its own work. Veldo achieves that with two distinct identities, set up once on the repository side. You do nothing here as a filer; this section is for whoever wires the tracker.

  • An admin identity performs the one-time board bootstrap (provisioning statuses and the workflow) AND the fencing described below. It is used only for setup, by a person with tracker-admin rights.
  • A separate, non-human service-account identity does the runtime writes (status transitions, comments, the ready-to-test reassignment) as the fleet works. It is a distinct principal, so its actions are attributable to the automation and, crucially, it can be RESTRICTED. It is fenced OUT of the terminal approval and decision states, so it can advance a ticket through the working states but cannot move one into "approved", "decided", or "rejected". Only the approver group can.

A principal can never fence or unfence itself: the fencing is an admin act, and the service account has no group- or workflow-admin permission, so it cannot reach the endpoints that would change the fence. This is configuration, not convention.

Standing up the service-account identity and its OAuth credential#

The runtime writer authenticates as a service account using an OAuth 2.0 client-credentials grant (a machine-to-machine credential with no interactive login and no human user behind it):

  1. Create a service account (a non-human account) in your identity provider or tracker admin, dedicated to the automation.
  2. Create an OAuth client-credentials app bound to that account and record its client id and client secret. Put each in your secrets store; the config references them, it never holds the raw values.

  3. Grant the credential the MINIMAL scopes it needs and no more:

    • read:jira-work
    • write:jira-work
    • read:jira-user

    Do NOT grant it group-admin or workflow-admin scopes. Withholding those is what makes the fence structural: even if asked, the service account cannot alter groups or the workflow restriction.

A client-credentials token is short-lived and carries no refresh token; the runner fetches a fresh one from the token endpoint and re-fetches when it lapses. The connection drives the tracker's API GATEWAY, not the site URL, because a site-URL call with basic auth does not accept a service-account token.

The auth-mode config#

The jira-cloud tracker block in .veldo/trackers.json selects the auth mode by reference. The default is unchanged, so an existing basic-auth setup keeps working:

"trackers": {
  "primary": {
    "kind": "jira-cloud",
    "base_url": "https://YOUR-SITE.example",
    "auth": "basic",
    "email": "YOU@example.com",
    "token_ref": "env:YOUR_TOKEN_VAR"
  }
}

To run the writes as the fenced service account, switch that block to the OAuth mode with secret REFERENCES (never the raw client id or secret):

"trackers": {
  "primary": {
    "kind": "jira-cloud",
    "base_url": "https://YOUR-SITE.example",
    "auth": "oauth-client-credentials",
    "client_id_ref": "env:YOUR_CLIENT_ID_VAR",
    "client_secret_ref": "env:YOUR_CLIENT_SECRET_VAR",
    "project": "YOUR_PROJECT_KEY"
  }
}

If your cloud_id is known you can set it on the block to skip the one-time lookup; otherwise it is resolved once from the credential's accessible resources.

The fence config#

The board bootstrap fences the board in the same pass, driven by a fence block under bootstrap. Everything is by reference, so nothing about your organization is baked into the tooling:

"bootstrap": {
  "project_key": "YOUR_PROJECT_KEY",
  "fence": {
    "agent_group": "YOUR_AGENT_GROUP",
    "approver_group": "YOUR_APPROVER_GROUP",
    "agent_account_id": "YOUR_SERVICE_ACCOUNT_ACCOUNT_ID",
    "terminal_states": ["Approved", "Decided", "Rejected"]
  }
}

When veldo jira init runs, it ensures both groups exist, places the service account's account id in the agent group and NOT in the approver group, and restricts each named terminal transition so only the approver group may fire it. It is idempotent (a re-run changes nothing) and it fails loud by name if you name a terminal transition your workflow does not have, rather than silently skipping it. Omit the fence block and the board is provisioned but not fenced.

What the live provisioner actually does (the proven Jira REST shapes)#

The live company-managed provisioner is reference-wired (it needs a real Jira and a scoped admin token, so it never runs in the gate; the gate proves the bootstrap logic over a fake tracker). Its Jira Cloud REST v3 calls are the exact ones proven against a real board, so you can audit them:

  • Statuses are GLOBAL. A company-managed lifecycle status is created with POST /rest/api/3/statuses, scope GLOBAL, its category mapped onto Jira's TODO | IN_PROGRESS | DONE. Existing statuses are read from the paginated GET /rest/api/3/statuses/search (create-or-reuse by name).
  • The workflow is edited through the modern bulk API. The provisioner reads the workflow via POST /rest/api/3/workflows, VALIDATES a change via POST /rest/api/3/workflows/update/validation (a wrapper request), and APPLIES it via POST /rest/api/3/workflows/update (the bare request). Existing statuses are kept, so an active workflow needs no status migration; every status carries a generated reference id and every transition carries an id.
  • The fence is a workflow transition condition. Each transition landing on a terminal status is restricted with the system:restrict-issue-transition condition scoped to the approver group. Groups are addressed by id: created with POST /rest/api/3/group, resolved by name with GET /rest/api/3/groups/picker, and membership is read and written through GET /rest/api/3/group/member and POST/DELETE /rest/api/3/group/user.
  • Issue types are attached, never faked. The bootstrap attaches an existing instance issue type to the project's issue-type scheme (PUT /rest/api/3/issuetypescheme/{schemeId}/issuetype); a type your instance does not have fails loud rather than mapping to a wrong type.

Adding a new decision issue type (an admin one-off, optional)#

The bootstrap only ATTACHES issue types that already exist in your Jira instance (Epic for plans, Task for specs by default). If you want a dedicated issue type for human decisions (for example a "Decision" type) and your instance does not have one, that is a one-time admin action, separate from veldo jira init: create a new standard issue type with POST /rest/api/3/issuetype (type: standard, hierarchyLevel: 0), then add it to your project's issue-type scheme with PUT /rest/api/3/issuetypescheme/{schemeId}/issuetype. A hierarchy-level-1 type such as Epic cannot be created this way and must already exist. Once the type is in your instance, name it in bootstrap.issue_types and the bootstrap attaches it like any other.

A full round-trip, walked through once#

Concretely, start to finish, with a bug:

  1. You file it. You open a Jira bug: "Checkout total is wrong when a coupon is applied." You add the label veldo-repo:web-app. That is the whole of your job at intake time.
  2. Intake runs. Someone runs /veldo:intake on your ticket. Veldo reads it, resolves web-app from the label, reproduces the wrong total as a failing test (that becomes AC1), and drafts a spec in the web-app repository with your ticket linked in intake_source. Had you forgotten the label, intake would have refused by name rather than pick a repository for you.
  3. The owner finishes the draft and marks it ready. The moment it is ready, the mirror moves your Jira ticket to "To Do" (per the status_map above). You did not touch it.
  4. The change is built and reviewed. When a review verdict is recorded, the ticket moves to "In Review". You can watch the ticket and know exactly where the work is without asking anyone.
  5. It ships. The spec ships and merges; the mirror moves your ticket to "Done" and posts a closing comment with the evidence links (the spec, the gate commit, the reproduction test, the review verdict). The ticket is now a true, closed record, and you never hand-edited its status once.

A Confluence requirements page runs the same way, except intake takes AC1..ACn from your page's Acceptance Criteria instead of reproducing a bug, and the mirror posts back to the tracker issue the change lands on (a wiki page has no status workflow of its own).
