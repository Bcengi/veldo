## Verdict: NOT SOUND

The batch machinery itself (assembly, hook, gate once, inventory, one compare-and-swap, re-land) is
well built and its tests and falsifiers have teeth. It is not sound as a delivery of the written ACs
because the owner's command does not start a batch in the product, and the class that would land
one checks no authority of its own.

## Findings

F1 (AC1, correctness; blocking). AC1: "the owner's command (Telegram /batch <project>, or the UI's
project view) starts a batch". No production construction of Intake passes `batches=`
(engine/.veldo/control_service_projects.py:336, engine/.veldo/control_service_api.py:175,
engine/.veldo/control_workflow_cycle_pm.py:654), so batch_started returns None and the message falls
through to ordinary intake (engine/.veldo/control_intake.py:297-302). The UI ships a live "Start batch"
button (engine/ui/src/views/ProjectsView.vue:107) that, today, sends `/batch <project>` into ordinary
intake: the owner's command creates an intake proposal instead of a batch. The only exclusion in the
spec is the automatic start (VELDO-0240); nothing defers the command's wiring. Either wire the starter
(principal check, eligible units from the store, ask through VELDO-0068, fix_round, receipts) or hide
the button and amend the spec with the owner.

F2 (AC3 and the threat model, security; blocking, same root as F1). The class enforces no authority:
Batch.land accepts any dict whose subject equals the public self.subject() and its digest
(engine/.veldo/control_batch.py:598-614); there is no VELDO-0068 settlement, principal or store record
behind the grant (suite 129 line 369 builds one from b.subject() itself). eligible() trusts a
caller-supplied `review.state == 'passed'` that is not bound to the reviewed commit
(control_batch.py:150-162). The single-unit path reads both from the authority store
(engine/.veldo/control_landing.py:622-640). "One owner approval binds the exact candidate" and "no unit
lands without its own review" therefore hold only if the unwritten wiring of F1 supplies them. Tip and
unit-list binding, stale refusal and re-ask, red refusal, other approvals by name, and acceptance of the
gate observation against the tip are correct.

F3 (AC3, correctness; minor). In the push path, a push that succeeds followed by a failing ls-remote
raises Refused (control_batch.py:654, default ok=(0,)), caught at control_batch.py:624-627: the trunk is
at the tip but the batch stays green with no receipts, and a retry finds the lease broken and reports
trunk_moved. Conversely any non-lease push failure with the trunk still at the watermark is recorded as
trunk_moved (control_batch.py:656, 628-631). Read the trunk with ok=None and classify by what was found.

(a) Live service creates no batch starter: required by AC1 in this ticket (the command, from Telegram
or the project view, starts a batch; only VELDO-0240's automatic start is out of scope). Finding F1, and
F2 depends on it.
(b) Batch receipts not in the authority store: AC3 as written asks a revision_landed receipt per unit
naming the batch, which the batch record and the receipt callable give. Not a standalone finding; it is
part of the F1 wiring (the starter must also source "landed" from the store, or a landed unit is batched
again).
(c) Reading the hook from the project file: owned by VELDO-0253, which AC1 names as the hook's source and
depends_on lists. Not a finding here. Note for VELDO-0253: the hook runs unconfined with cwd in the
candidate clone, so a hook argv that names a file in the repository runs the units' merged copy of it;
the threat model's "hook reaching outside the clone" should be settled there.
