## Verdict: NOT SOUND

Two defects need fixing on this branch, and both fixes fit inside the spec's footprint. The rest of the build
is careful: the scan masks correctly, reports only, has one entry, and the default launch path is unchanged.

## Findings

1. BLOCKING, AC2. `.veldo/secret_scan.py:150` reads its formats from `secret_scan_patterns.json`. The
   installed service layout copies only the `.py` closure and `runtime/` assets
   (`control_service.closure`, `runtime_assets`). I checked: `closure()` includes `secret_scan.py` but no
   non-.py file. So on an installed receiver the run-end scan (`control_launch.py:1525`) and the landing
   scan (`control_launch_work.py:237`) raise FileNotFoundError on every call. The error is swallowed to
   stderr, so AC2's run-end and landing-candidate triggers do nothing in production. OPEN.md item 6 says the
   fix is outside the footprint. That is not true: putting the formats list into `secret_scan.py` itself
   (in the footprint and protected_paths) fixes it.
2. BLOCKING, AC3, risky path. `control_launch.py:1946` passes `cwd or os.getcwd()` as `--worktree`. For a
   risky engine run (not a conversation), `cwd` is None, so the confined runner gets the receiver's own
   working directory as its writable worktree, not the dispatch's clone work tree (`_engine_cwd` already
   computes that). `runner_argv` (`control_launch.py:390-396`) also passes no `--client`, so the runner
   hands the engine none of its CLI files. A risky engine run therefore either fails to start or is
   confined with the wrong writable root. No row covers this (OPEN.md item 7 admits it). The fix is in the
   footprint: use the clone work tree and the engine's client, and add a row that drives
   `Receiver._spawn` for a risky launch.
3. Non-blocking, AC1 scope. See ruling (a): inherited host environment and adapter environment values are
   not covered.
4. Non-blocking, design. The run-end scan runs synchronously before the end is recorded
   (`control_launch.py:1525`) and walks the whole clone work tree, up to 16 MiB per file. On a large tree
   this delays recording the end. Each run end also re-reports every credential already present in the
   project tree. Better to scan only the files the run changed, or run the scan after the end is recorded.
5. Non-blocking, evidence. `ac1/canary-run` (suite 127, lines 145-166) scans a hand-built environment and
   argv; it never goes through the launcher. The spec's AC1 falsifier says "the canary row finds it". With
   the falsifier applied, only the static rows went red, not the canary row.
6. Minor. `confined_runner_problem` runs a full `namespace-selftest` launch, with a 120 s timeout, on every
   risky launch. This is opt-in only, but it could be cached per receiver.

## Rulings

(a) AC1 "passes in part": agreed, and the check is NOT complete over every way a credential reaches a run
today.
- What it does cover: the call graph from launch sites to keystore or secretref resolution. It finds
  exactly `control_launch.py:Receiver._spawn` (the VELDO-0158 MCP catalog credentials, which VELDO-0257
  removes). That covers the MCP server config handed to a run through the baseline. The memory handoff
  (VELDO_MEMORY) carries locations, not credentials. Git push credentials
  (`control_git_identity_transport.credential`) are control-plane landing, not run.
- What it misses:
  - The run environment is built from the receiver's own `os.environ` (`control_launch.py:1911`) and
    filtered by a deny-list (EXEC_STRIPPED, session prefixes, login names). Any outside-service
    credential in the receiver service's environment reaches every run.
  - Literal values in an adapter's `environment` configuration are passed through as configured.
  - Credential files read by plain `open`/`read_text` are not modelled. Probe run: a credential file read
    into `engine_environment` left suite 127 green.
  - No production trigger scans a run's environment or command line; the run-end scan reads files only.
- Does the AC require more than this build does? Yes, in one respect. Its rows require one real launch of
  each kind on each engine with canaries in the keystore, and that is not built. As written, the static
  row's letter ("resolves a keystore reference or reads a credential") is met for the keystore. The
  claim ("never ... an environment") is not met while host-environment inheritance stays a deny-list.
  Route that to VELDO-0257 or a new ticket, or amend AC1 to say it is keystore-scoped.

(b) Suite 128 and `scripts/gate_unconfined.json`: an entry is the only way for the AC3 risky row to be
evidence inside the gate.
- The alternative already in the repository, suite 102's SELFTEST SKIP when the helper cannot make the
  tree, would leave the row unasserted in the gate, which is not acceptable for an AC row.
- A row-scoped entry adds nothing, because the suite has one row.
- Exact entry, appended to "suites":
  `{"suite": "128_veldo_0254_confined_runner", "reason": "nested namespace: starts the confined runner of VELDO-0208, whose helper cannot be judged inside the gate's confinement"}`
- This is a protected change (policy floor high), so it is the owner's to make. Suite 128 passed here in
  the unconfined context.

(c) Deferred items in OPEN.md:
- Item 4 (held gate credentials passed to the scan) belongs to VELDO-0251 and VELDO-0253. Confirmed.
- Item 3 (removing the VELDO-0158 site) belongs to VELDO-0257, per the spec's Out of scope. Confirmed.
- Item 2 (AC1 canary row) belongs there only in part. Only "declared fixture services" is VELDO-0253's.
  The keystore already exists (`control_credential_keystore`, used by suite 85_veldo_0158). So a
  real-launch canary row for each launch kind, with fixture canaries in that keystore and no catalog
  server selected, can be built now and is this ticket's.
- Item 5 (owner notice through Veldo's own channel) is not deferred to 0251 or 0253. It is this ticket's
  AC2, blocked only by the footprint, which needs a spec amendment.
- Item 6 is finding 1.

(d) No sandbox or fence on normal runs: confirmed.
- `runner_decision` defaults to `default`, and `runner_argv` then returns the argv unchanged.
- The selftest and refusal paths run only for a launch marked risky.
- The diff adds no namespace, network, name-resolution or filesystem change to the default path.
- ac3/default-reaches shows a default run reaching loopback TCP, a Unix socket and a local HTTP service.
