Borrowed login credential persistence

Root cause
The suspected mechanism is confirmed by an offline reproduction, not by replaying the owner's
production login. live.py previously symlinked the credential file into a temporary profile.
The fake engine saves a rotated refresh token with os.replace. This replaces the symlink, leaving
the original login with its old refresh token. No production credential was read or used.

Audit
Searches across proof, scripts, engine, bin and .veldo for credential filenames, profile environment
variables, copying and linking found two production borrowing paths: proof/VELDO-0127/live.py and
scripts/agent_sandbox.py (canon: engine/scripts/agent_sandbox.py). Format probes create synthetic
credentials. The ordinary control engine adapters use the account profile directly. Outside this
repository the myday runners (account_lease.sh and the scripts that source it) lease each login
with flock on <login dir>/.runner-lease and start the launcher holding it.

Host review of the first implementation (9cc5bbf5) and what changed
1. Suite 102 regressions. The source-order row now anchors on run_tree's fork mask; no lock file
   is left in an account (the sibling .veldo-lock is gone, the lease file is the runners' own and
   is never created by a borrow); the live-launcher row's second start borrows no login; the
   start-time check no longer replaces the credential, so write-back-is-atomic-replace is
   deterministic and the full account_state() comparisons are back.
2. One lock. take_lease holds <login dir>/.runner-lease for live.py and the launcher. The
   launcher accepts an inherited descriptor that holds it (its runner's) and takes it itself only
   when it has none; a second borrow in one process is busy. The runners' fallback path already
   runs under the runner's lease, and now live.py takes that same lease, so a fallback run waits
   for a live capture instead of interleaving with it. The myday runners now also stop with 74,
   never falling back, when the preflight ends in a recovery (commit in that repository).
3. SIGKILL. Each borrow journals its sources and digests outside the scratch before an engine can
   rotate. The next launcher or live start turns the journal of a run nobody holds into a recovery
   when a copy changed, reports it, and the stale sweep never removes an unsettled scratch. A
   guard process forked by live.py holds the lease and scratch; if live.py dies it stops the slice,
   writes back, then releases the lease.
4. Exit status. CredentialRecovery is no longer a RuntimeError; the launcher exits 74 with
   "CREDENTIAL RECOVERY REQUIRED", the run's own exit status and the restore command.
5. The start-time check creates and removes a sibling temporary file only.
6. Suite 102 sends journals and recoveries to its own directory (XDG_STATE_HOME) and removes
   each recovery a row creates; suite 103 does the same.
7. restore-login (scripts/agent_sandbox.py restore-login [dir] [force]) and the procedure in the
   spec. A recovery is written by copying into the persistent store, not by renaming the scratch;
   if that fails the scratch itself is kept.
8. The signal mask around write-back has its own suite 103 row and falsifier.

A further fix found by running suite 102 repeatedly: a stop during the tree's start was forwarded
to the tree and then the tree was killed; the forwarded TERM sometimes reached a command that had
already started. Main failed the row rarely, the first implementation often. A stop is now only
forwarded once the tree has started; before that the tree is killed.

Limits
A Claude or Codex CLI run directly on a leased login takes no part in the lease. A confined agent
can force a recovery by corrupting or deleting its copy; the source is left alone. live.py keeps
its copies in the runtime directory: a reboot during a capture loses a rotation made in it (its
journal then reports that). The runners' unconfined fallback CLI runs with the lease descriptor
closed; the runner holds the lease while it waits for that CLI.

Verification
Foreground on the host: suites 102 (three runs), 103 and 104, and falsify.py (seven mutations,
all detected), with logs here and a summary in diagnostics.json. The myday dry test ran against
this checkout. The complete gate, independent review, merge and push are not part of this work.
