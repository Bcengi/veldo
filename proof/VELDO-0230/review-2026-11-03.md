## Did any check lose its meaning?

For each moved reference, what can still make the check fail:

- MODEL_TOOL_MODES (was a code literal) is now the record's catalog modes. `qualified_baseline` now checks the
  record against itself (modes against the record's catalog), so it can fail only on a broken writer or a
  hand-edited record (mutant role127-model-baseline-unchecked is still killed). Drift between the binary and
  the record is caught by the bind digest pin plus suite 126's reproduction. Acceptable.
- Suite 86 review/codex-mode compared against an independent 0.154.0 investigation file; it now compares the
  writer's modes against catalog-fixture.json, which qualify.py writes from the same catalog. It still fails
  when the writer drops or alters modes (mutant role127-model-modes-omitted). "These are the binary's modes"
  now rests on suite 126 alone.
- Claude built-in plugins and skills moved from code into the record. The init comparison still compares the
  live binary's init event with the record, so it keeps its meaning.
- Extractor default binaries now come from the engines record. Check mode still compares a fresh read of the
  binary with the table. Meaning kept.
- Suite 79 pin/qualified-record still re-runs the production writer on the installed binary and compares it
  with the shipped record, and cross-checks version and digest with two independently extracted tables. Meaning
  kept.
- Suites 78, 79, 80, 81, 83, 85: the fakes' version and package version now come from the engines record. These
  rows test module behavior on a fake, so the source of the version string does not weaken them.
- Suite 126 is the anchor that keeps every generated reference honest. Its covers row is weaker than it claims
  (finding 4), and it does not cover the VELDO-0156 captures (finding 1).

Net: no row turned into a self-comparison that can never fail. The cost is that one suite (126) now carries
the binary-equals-reference guarantee for every moved table, so findings 1 and 4 matter more than they look.

## Recommendation on the resource readers (suites 86 to 90)

AC3 does not cover them as written. They are not an unknown feature or an unknown tool: they are known tools
under an explicit owner rule (Telegram 29400/29401, none without a selected server). They also cannot be
switched "off" on 0.166.0. I forced each of the 25 non-tool features off on a loopback probe and the readers
stayed; the 20 unknown features are already off. With no MCP server configured they have nothing to list or
read, so they grant nothing. I recommend recording them as offered but not granted: qualify.py reads from its
loopback capture which readers the binary offers without a server, per tool mode, into the record's
mcp_resource_rule. The wire comparison accepts exactly that recorded set for a no-server run and still refuses
any other extra tool. A role can never grant them without selecting a server. That keeps fail-closed for
everything else, matches "veldo can't be a handcuff", and makes the next binary that changes this a re-run
instead of a code change. It is a small code change (codex_expected_tools, the record writer, and the
expectations in suites 86, 88 and 89), not a re-run. Because it amends an owner rule, it needs Dmitry's yes in
one sentence before it is built.
