## Findings

1. BLOCKER: the production mutation stage refuses.
   - Where: `scripts/check_gate_mutations.py:1385` sets `admit=True` whenever
     scripts/gate_graph.json exists. `scripts/check_gate_mutations.py:352` then raises
     invalid_resource_requirement because the graph's mutation node has `manager: exclusive`.
     Without the ledger channel, :348 raises worker_launch_error instead.
   - Effect: every canonical or landing gate in this repository goes RED at the mutation stage.
   - Test: suite row admission/aggregate-handoff-refused
     (`scripts/suites/115_veldo_0219_measured_admission.py:382`) asserts this refusal as a pass.
   - Consequence for the criteria: AC2 ("starts it only when the ledger grants") is met only with
     a fake client. AC1's recording never runs in production, because `record_case_resources` is
     gated on admission.
   - Root cause: a dependency gap that needs protected changes to VELDO-0216 (gate_schedule.py and
     gate_graph.json). It is recorded in OPEN.md, but it means no criterion holds end to end.
2. HIGH: no measured admission when there is no graph.
   - Where: `scripts/check_gate_mutations.py:85` and `:88`.
   - Effect: the engine ships no scripts/gate_graph.json, so `admit=False` and
     `PARALLEL = 2 x CPUs` becomes the actual concurrency with no measured claim. A 20-core host
     goes from 16 to 40 workers.
   - Why it matters: AC2 removes the 16 cap only because the ledger replaces it. The rollback text
     assumes 2..16.
   - Fix: without admission, keep the old clamp, or refuse by name.
3. MEDIUM: AC4 has not run.
   - The force-fresh canonical gate and the fixed-sixteen canonical falsifier are deferred.
     qualification.py has been tested only on synthetic captures.
   - The 4,000-second claim is unproven.
4. MEDIUM: AC1's unit accounting is incomplete.
   - Where: the `WorkerMeter.sample` polling in `scripts/mutation_ownership.py`.
   - Effect: a unit that starts and stops between discovery polls is missed, and a recreated
     cgroup path can reset its counter. OPEN.md shows that existing
     control_containment/control_service code stops units during the worker's lifetime, so
     "read before cleanup" does not hold.
   - What is needed: lifecycle-bound capture, or a spec amendment to sampled accounting.
5. LOW: the CPU claim mixes runs.
   - Where: `scripts/check_gate_mutations.py:276-277`.
   - Effect: the claim is the largest CPU seconds of any run divided by the fastest elapsed of any
     run. It is conservative, but it is not "the claim taken from the faster run" (AC1). Either
     state it in the spec or compute cpu/elapsed per run and take the largest.
6. LOW: the admission log does not name the resource that blocked a worker.
   - Where: `scripts/check_gate_mutations.py:386`.
   - Effect: every admission event says `resource='ledger'`. The observability contract ("waited
     ... for which resource") is unmet until the ledger reply names the refusing resource
     (OPEN.md).
7. NOTE: the VELDO-0123 per-case cap now uses m.
   - Where: `scripts/check_gate_mutations.py:101` and `:123`.
   - Effect: with a floor, m (not the parallel count) now enters the VELDO-0123 per-case cap. When
     m is below 8, the cap loosens, by up to 4x at m = 2.
   - This is consistent with AC3's wording, but it does change the effective cap. The human
     approver should see it.
