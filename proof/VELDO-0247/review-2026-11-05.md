## Per AC

- AC1 (closed check config). control_workflow.py `_check_problems`, `_literal`, `_field_problems`: an exact key
  set at config, branch and condition level; comparisons limited per type; `type(...) is int/bool` (a bool is not
  a number); the text pattern is ASCII-only, at most 200 chars, with CODE_LIKE checked first. `evaluate`/`_holds`
  compare values as data. Nothing is evaluated or interpolated. A `{node, result}` source must come from an
  assignment on every path (`ran_before`).
- AC2 (one branch, re-checked). The cycle supplies the field values from the store (`_fields`), re-evaluates
  with WF.evaluate, and refuses unless the runner's whole decision and port equal its own (`_judge_check`,
  control_workflow_cycle.py:563-567). The same check runs for checks inside branches (`_block_step`). When
  the runner fails, the cycle's own problem name is used. The runner never chooses the route. On the Line the
  check is evaluated in process (control_service.py `step_check`), and a recorded route that differs from it is refused.
- AC3 (fan-out, join waits). The runner uses Send for every unarrived branch in one superstep, with a
  reducer-merged `branches` state. The cycle refuses unless every moved branch shares one superstep. The join
  runs only when every branch has arrived, enforced on both the runner side (`parallel`) and the cycle side
  (`_block_step`). The width is at most 8 at save (`fan_out_too_wide`) and in the runner (MAX_BRANCHES). On the
  Line, `_walk` walks every branch in one pass on forked state and goes on past the join only when no branch is
  still waiting. A branch that stops (offered, holding, limited, refused check) leaves the join waiting. A walk
  problem in any branch (budget, missing transition) stops the whole pass by name.
- AC4 (approval on every path). VELDO-0241's product walk is reused. Every check port, otherwise included, is
  an edge it walks, and each fan-out branch is walked to the join. `branch_approval_problems` refuses an approval
  or an outward step inside a branch.

## Findings (non-blocking)

1. control_workflow_cycle.py:594 and :873. The step budget is checked only before an exchange. One superstep
   adds len(moved) steps (up to 8), so a cycle can end up to 7 steps past budget.steps before the next loop
   refuses it budget_exceeded:steps. The overshoot is bounded and has no outward effect: branches hold no
   approval or outward step, and dispatch happens after the budget check. Still, the spec Notes say a wide
   fan-out "cannot run past the cycle budget". Suggest refusing a superstep whose moved count would pass the
   budget. The Line's `_walk` is strict.
2. control_workflow_unit.py:140 (`parallel_problems`). Two stations of one kind in parallel branches are
   refused, so the spec's own normal-use example cannot run on a unit's Line (a copy branch and an image branch
   as two builds). Line parallelism is only across different station kinds (for example build with review).
   The cause is control_launch's one active dispatch per unit and station, which is outside the footprint. This
   is disclosed in OPEN.md item 1 and named in the taxonomy.
3. Spec frontmatter (error_taxonomy) was changed after owner approval (History 2026-11-05, "by the lead"; no
   owner Telegram reference). The ACs are unchanged, but the owner should know that parallel_station (finding
   2) narrows what the Line can do in parallel.
4. Engine and .veldo copies are byte-identical. The footprint entries packs/*/.veldo and init_scaffold.py are
   not touched, and no packs copy exists.
