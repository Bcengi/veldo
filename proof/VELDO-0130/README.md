# VELDO-0130 proof, phase 1

Phase 1 of the authenticated factory API: passkey sign-in, server-side sessions, the API as its own
enrolled channel edge, and AC1 and AC3 for the auth, messages and decisions route families. AC2 (read
models and live events) and AC4 (configuration and operational actions) are phase 2. Specification status,
risk and `.veldo/policy.yaml` are unchanged. This proof is for independent review; it is not a
self-approval, and the canonical gate is run by the lead, not recorded here.

## What was built

Six new engine modules, each byte-identical under `engine/.veldo/` and laid by `init_scaffold._FILES`
(none is validator substrate):

- `control_api.py`: the service. Plain HTTP with ThreadingHTTPServer on a loopback address only
  (`listen` refuses any other), the Host check, the 64 KiB body cap and Strict-Transport-Security on every
  response. The one published route table `ROUTES` (name, method, path, family, session, exact body
  fields, authority operation) with handlers registered by route name; `route_problems` compares the two.
  Sessions in memory behind create, find, touch, end, end by credential and end by principal; the
  `__Host-veldo-session` cookie (only its SHA-256 kept), the per-session anti-forgery token, the Origin,
  Sec-Fetch-Site and Content-Type checks on every write, 30-minute idle and 12-hour absolute expiry.
  Registration and possession ceremonies write a 0600 pending file (15 minutes, at most three); a failed
  ceremony ends its registration and an enrolled one stops being pending. `follow` ends sessions from
  committed journal records (a revoked api_credential or membership). A body naming principal, actor,
  actor_id, decider or any unknown field is refused `invalid_input`.
- `control_api_webauthn.py`: clientDataJSON and authenticatorData checks with json and struct, the
  signature by the openssl command line (fixed argv, no shell, empty environment, 10 seconds, a fresh
  0700 directory, exit status only). ES256 reads the signed bytes on standard input; Ed25519 reads them
  from a file in the same directory, because OpenSSL 3.0.13's pkeyutl cannot size a pipe for a one-shot
  verification (measured on this host).
- `control_api_credentials.py`: the `api_credential` store kind (owned by its two commands) and the
  steward-signed `enroll_api_credential` and `revoke_api_credential`, with the possession proof checked
  again at the host, and `revoke_as_member` for a steward's own session. A credential is current only
  while its principal is a current person member, so revoke_membership ends it with no second write.
- `control_api_assertion.py`: `veldo.api_assertion/v1` and the one domain request each operation derives
  (VELDO-0126's API intake request unchanged; VELDO-0068's API answer).
- `control_api_signer.py`: the protected signer's "api" purpose (reached through control_signer_answers
  for the enrolled api edge) and the API's client of it.
- `control_api_authority.py`: the authority's own recheck (edge signature by ssh-keygen, liveness, the
  credential and member, the boundary) and execution into intake, settlement or revocation.

Changed: `authority_contract.py` gains `EDGE_CHANNELS` with the "api" edge and `edge_channel()` (kept out
of `CHANNELS`, the VELDO-0020 answer-channel registry that settle() ranks by and suite 33 pins);
`control_channel_enrollment.py` enrolls channel "api" (its `metrics` still reports the Telegram edge's
pending work); `control_signer_answers.py` hands the api edge to its own purpose. The committed intake and
settlement records keep their own provenance unchanged; the credential id, session handle and assertion
digest are in the authority's observation of the request id.

## Rows, falsifiers and red record

Suite `scripts/suites/71_veldo_0130_api.py` (about 7 s), 16 rows: real SQLite store, real OpenSSH
signatures on every command, journal record, possession proof, edge assertion and domain request, the
actual protected signer process, VELDO-0066 Acquirer, VELDO-0065 presenter, VELDO-0126 intake and
VELDO-0068 settlement over a loopback Bot API, and the API handler (over real loopback HTTP for the
transport row). It also passes in the stage environment (`env -i`, empty HOME, `GIT_CONFIG_GLOBAL=/dev/null`).

Passkeys come from a local browser stand-in: ES256 and Ed25519 keys generated by openssl in the fixture,
authenticatorData and clientDataJSON assembled byte by byte, signed by the openssl command line.

**The independent implementation.** Row `webauthn/independent-vectors` verifies four W3C Web
Authentication Level 3 test vectors (section 16, https://www.w3.org/TR/webauthn-3/, W3C Software and
Document License), copied into the suite as published: 16.6 (ES256, user verified) is accepted and refused
when its signature changes; 16.2 (ES256) and 16.11 (Ed25519) verify at the signature layer and are refused
for no user verification; 16.4 is refused as cross-origin. Each public key is the COSE x and y read from the
vector's attestationObject, wrapped in the fixed SubjectPublicKeyInfo prefix by hand.

AC1's declared falsifier is `body-actor-authorizes` (a decision authorized by the body actor_id, red on
`routes/body-actor-refused`); AC3's is `ui-answer-settles-again` (a second settlement for the UI answer
after Telegram settles, red on `decisions/one-ruling`).

`red-at-b84197b.json`: the current suite against the pre-change tree (`git archive b84197b`): all 16 rows
red, by assertion (no section raised). That tree has no API modules, so the suite drives what it has in
their place: no route answers, no verifier, no credential.

`python3 -B proof/VELDO-0130/drive.py` regenerates `mutations.json` and the diffs: every finding-130 mutant
reds its named rows by assertion, with the baseline and a no-op copy of each mutated module green.
Registry: `scripts/check_teeth_mutations.py --finding 130`.
