## Acceptance criteria

- AC1 (pause carries its reset, ends by itself). control_accounts._pacing refuses a window with no reset later
  than now (invalid_input:pause_reset) before anything is written, and stores the window's reset as the end;
  `paced` holds the account only while now < until, so it is selected again at the reset with no command;
  control_account_pool.choose folds the end into `until`, so no_account_until and the loop's timer wait for it.
  A later `observe` rewrites only `windows`, never `pause`. No pacing route touches `status`. Correct.
- AC2 (ceiling, relative and absolute, lapse, resume). Relative +N is added to the observed percent and stored
  absolute; 1..100 enforced after the addition; a window with no utilization is refused invalid_input:ceiling;
  same reset rule (invalid_input:ceiling_reset); replacement per window; resume clears the pause and all
  ceilings in one record. Pass-over at used >= value. Run in flight is untouched (control_reservations._check
  still reads only `blocking`). Correct.
- AC3 (Telegram and UI, owner only). Both routes reach the same Accounts.pause/ceiling/resume; the owner check
  (factory_owner: current person member, self-enrolled, both bootstrap roles) runs inside the store
  transaction, with now from the server clock on both routes. Telegram additionally requires membership at send
  time (control_intake._plan). The `end` action is accepted only when the command's principal is the writer's
  own service principal and no API or Telegram route can issue it. Answers name account, window and end in the
  configured zone. Correct.
- AC4 (journal). Each command and each end is one signed record; `history` reads the journal and keys each
  record by its own command id, so the `pacing` field copied forward by later observe/status writes is never
  double counted; lapse's command id is a digest of (account, kind, window, setting command), and the second
  pass finds nothing due. FactoryLoop.run calls lapse every pass (control_service.py:3394). Correct.

## Registry change (OPEN.md item 5)

Accounts._own re-registers the connection's OPERATION transition to the writing instance's bound
_in_transaction immediately before every store.execute (control_accounts.py:389, 445, 493, 544: _run, cap,
_pace, lapse). The store reads conn.command_registry inside execute (control_store.py:564), synchronously, and
the transition reads that same instance's `_command`, which was set on the line before. Every write path of the
class claims it, so one instance's (or one account's) command can no longer be judged by another instance's
last command. Correct.
