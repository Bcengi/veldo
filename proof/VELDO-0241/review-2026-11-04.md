## Findings

F1 (AC2, blocking). engine/.veldo/control_workflow.py:403 (approval_problems, second walk; same at
.veldo/control_workflow.py). The approval_not_last walk stops at any approval naming the outward node
(`if here in approvals: continue`), whatever port leaves it. The reachability walk (lines 379-387) skips
every `granted` edge out of such an approval, so a second approval reached only past the first one's grant
is never visited at all. Together, a definition where a build follows approval A's grant and then reaches
land through approval B's `stopped` port gets past both checks. Reproduced against
WF.definition_problems, the function save runs:

    build -done-> review -done-> gate -passed-> appa(owner_approval, approves land)
    appa -granted-> b2(build) -done-> appb(owner_approval, approves land)
    appb -stopped-> land            (appb -granted-> land or -> done: both accepted)
    land -*-> done

    definition_problems(...) == []

The path start..appa(granted)..b2(build)..appb(stopped)..land puts a subject-changing step after the
approval, and land is reached without any approval granting after that step. That breaks AC2's second rule
("no step that changes the subject lies between that approval and the outward node"). The check's own
docstring also says only `granted` passes on to the outward node. The suite rows (removed, side-edge,
build-after, build-after-land) do not include it.
Fix direction: in the second walk, follow only the non-granted edges out of an approval naming the target
(or reset `changed` only on its granted edge). Add a row with this shape.

Probes the check handles correctly (each refused with the named problem): a stopped->land side edge
(missing_owner_approval:land); a build reached only by a back edge from land
(land.trunk_moved -> b2 -> land: approval_not_last); an approval that names one land and grants to another
(missing_owner_approval for both); land as the entry; an approval naming itself (invalid_config, and
missing_owner_approval). A renamed approval kind (`approval`) is refused as unknown_step_kind. Parallel
edges are refused as duplicate_transition (from, port). Cycles: every cycle needs `max`
(unbounded_cycle), and both walks are visited-set bounded.

Runtime note (not a mitigation of F1 under the AC as written): the Line never offers a first land or passes
an approval node itself (station_step waits there), and the land station still requires the VELDO-0057
approval bound to the exact subject. So F1 is a save-time hole, not a demonstrated unapproved land today.

## Rulings on the open items

(a) No AC requires a fresh install to hold `code` as a saved revision. AC1 asks only that `code` "ships as
the default definition" and that a project with no binding runs it, and that is met. The sentence about
saving at setup is in Notes, not in an AC. Today a new project has no binding, so WU.resolve returns the
shipped `code` from .veldo/workflows/code.json (or the module's CODE copy in an installed service) as
version 0 (SHIPPED), and the unit pins that. To run anything else, the owner saves a revision (VELDO-0132)
and binds it with bind_workflow. The canvas cannot show `code` as a stored revision until a setup spec
saves it, so file that as a follow-up. The scaffold comment at engine/.veldo/init_scaffold.py:123
("and setup saves") overstates what happens.

(b) Inherited, not caused by this branch. A snapshot of main 043c2ef6 (git archive into scratch) fails the
same two rows when suite 101 runs alone. scripts/agent_sandbox.py and the suite file are identical between
043c2ef6 and HEAD. The snapshot also failed confined-stage/installed-pack-gate-green, but only because the
snapshot is not a Git checkout ("expected shared gitdir is unavailable"). That row passes on the branch.

(c) No rule makes the numeric prefix unique. The unique key is the suite name (manifest `name`/`file`),
order comes from the manifest, and 28 prefixes are already shared (59, 65, 70, 86 and 113 among them). The
two names differ, so nothing has to move. The only clash is a textual append conflict in manifest.json and
requires.json, which whichever branch merges second resolves. If the owner wants one suite per number, the
later one should move: 0241's suite was added at 18:02, after 0234's at 15:56. Since 0234-0235 also adds a
suite 128, 0241's would become 129.
