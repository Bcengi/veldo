## Findings

1. HIGH: AC1's suite text is not met (OPEN.md section 1). Files:
   scripts/suites/113_veldo_0188_project_lines.py:200 and :275.
   - AC1 requires the installed service, a second project created through VELDO-0143's provisioner and a
     third adopted through VELDO-0161.
   - The suite instead runs Service in its own process and simulates take-on by setting what
     Service._take_on sets. It uses the author configuration the provisioner would write, without running
     the provisioner, and it bypasses the account pool.
   - The owner's 2026-10-23 decision moved VELDO-0143 AC3's first-unit observation into this row. It named
     proof/VELDO-0143/round4/first-unit-for-0188.py as the seed. Suite 113 does not use that seed.
   - The footprint is not the obstacle: the provisioner and the adoption effect can be called from suite 113.
     The only real obstacle is runtime cost. I do not accept this point without an owner waiver.

2. HIGH: production exceptions that contradict the acceptance text (OPEN.md section 2, items a to c), in
   engine/.veldo/control_service.py:
   - :2590 (2a): on a repository the work configuration names, a project the store cannot staff still
     serves with the work configuration's roles. That includes a role that cannot be dispatched and a
     missing team. AC2 says such a project is left without a Line, and AC1 says the work configuration
     supplies a Line only when no project record names the repository.
   - :2646 (2b): on a work-configured repository, a closed project's Line is never removed. AC3 requires it
     to leave the loop and the status. This case covers the enrolled factory repository, which is the
     most common one in production.
   - :2596 (2c): whether the refusal stands depends on whether the receiver adapters name an engine in
     L.ENGINES. That is a test-fixture accommodation inside production logic.
   - :2508 / add_line: VELDO-0143's new-project pass still adds a Line outside a loop pass. AC1 says
     "Nothing else changes the set".
   - All four exist to keep suites 83, 92, 93 and 110 green, and none of those suites was run here.

3. MEDIUM: the "only at a journal-woken pass" rule has no teeth. engine/.veldo/control_service.py:2735.
   - Mutant: replace `if 'journal' in report['sources']:` with `if True:`. Suite 113 stays green at 14
     passed.
   - Every pass in the suite is woken by journal_pass, so a Line started by a timer or any other source,
     which the threat model names, is never exercised.

4. LOW: the `closing` early return is not load-bearing in the tests. engine/.veldo/control_service.py:2052.
   - Mutant: delete that return. Suite 113 stays green.
   - "Offers nothing / no re-run" currently holds only because VELDO-0076's Gate refuses a canceled
     project's units.

5. LOW: a paused project at restart is untested. engine/.veldo/control_service.py:278.
   - Mutant: `PROJECT_OPEN = ('ACTIVE',)`. Suite 113 stays green, because an existing Line is merely left
     untouched.
   - A service restarted while a project is paused would build no Line for it, and no row covers that.

6. LOW: the refusal counter is cumulative per pass rather than per project. engine/.veldo/control_service.py:2638.
   - The status shows `invalid_input:line:role:adapter: 6` for the single refused project shoal.
   - The observability text asks for projects refused per pass.

7. LOW: two edge cases.
   - missing_authority:team:<project> is never exercised. It is in the error taxonomy, not in an AC.
   - :2619: if a work-configured Line's receiver configuration changes, the Line is set closing. It is
     never removed (it is in work_roles) and never rebuilt, so it offers nothing forever.
