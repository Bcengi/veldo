# VELDO-0156 proof: every Codex run on the everything-off baseline, behind the paid-API guard and the environment strip

Built on branch build-veldo-0155-0156 from 45ee21bb, together with VELDO-0155, whose trusted wrapper strip
this qualifies for Codex (proof/VELDO-0155/README.md describes the shared receiver path).

## The design as built

**The baseline, qualified with the binary.** `control_engine_codex.BASELINE` names every switch, each the
0.154.0 binary's own (`codex-baseline.json`, below): the exec options `--ignore-user-config` (the account
profile's config.toml is not loaded; the login still comes from CODEX_HOME) and `--ignore-rules` (no user
or project execpolicy rules), then the generated configuration as `-c` overrides (`generated`):
`project_doc_max_bytes` 0 (the binary's own default is 32768), `forced_login_method` chatgpt (one of
chatgpt and api), `cli_auth_credentials_store` file (one of file, keyring and ephemeral),
`skills.bundled.enabled` false (the bundled skills the binary installs into the profile's skills/.system
never load, listed or named) and `skills.include_instructions` false (no skills section), then `--disable
apps` (the apps feature, the login's ChatGPT connectors, off; it fails closed). No hook is generated and nothing is copied from the
account profile. The production writer
(`control_engine_codex.qualification`) records the baseline; `bind` refuses a record without it by name
before acceptance (`missing_evidence:engine_baseline:<version>`). The shipped record was regenerated by
that writer from the installed binary (its bytes and package manifest; nothing executed), unchanged but
for the baseline. The receiver splices the baseline right after the qualified flags, so an adapter's own
trailing arguments stay last, and keeps the generated configuration, as passed, in the run's own
configuration directory.

**The paid-API stop.** `login_problem` runs the pinned binary's own `login status` in the engine's
environment (its CODEX_HOME) before acceptance, reading the file store (`-c
cli_auth_credentials_store="file"`), and requires the binary's ChatGPT line (`Logged in using ChatGPT`, a
line of its own in the binary); any other of its lines (an API key, an access or personal access token,
Bedrock, workload identity, `Not logged in`) or none is refused by name (`paid_api:codex_login:<kind>`),
nothing accepted, reserved or spawned and no turn sent. The check never forces the login method: with it
forced the binary answers an API-key login with "ChatGPT login is required, but an API key is currently
being used. Logging out." and removes that login from the profile. In the run itself the forced method
makes the engine refuse any other login with that message before a turn, which is the second check.
OPENAI_API_KEY and CODEX_API_KEY were already stripped by VELDO-0062 (the OPENAI_ and CODEX_ families);
the receiver now reports the names it removed.

**The profile's own instruction files.** The binary reads CODEX_HOME's AGENTS.override.md, else its
AGENTS.md, into every prompt whatever the baseline says (its codex-home loader, separate from the project
document the budget turns off; no configuration switch tried removes it, `codex-rendered.json`), so
`profile_problem` refuses a profile holding either by name before acceptance
(`invalid_input:engine_profile:<name>`), nothing accepted, reserved or spawned. A relative CODEX_HOME is
resolved against the engine's working directory, which the receiver passes (THE ENGINE PROTOCOL's `cwd`),
and `login status` runs there.

**Skills named in the prompt.** A skill the prompt names (`$name`, anywhere in it, a JSON string too) has its
whole SKILL.md put into the model request whatever `skills.include_instructions` says (the binary's own
request captured on loopback, below). Only the bundled set has a switch that keeps it out
(`skills.bundled.enabled`, in the baseline). For the other four places no switch does, and the prompt is
not ours to scan, so `profile_problem` refuses each place holding anything, by name, before acceptance:
the profile's skills/ (`invalid_input:engine_profile:skills/<entry>`, the binary's own .system excepted),
the engine HOME's .agents/skills (`invalid_input:engine_home:.agents/skills/<entry>`) and the clone's
.agents/skills and .codex/skills, from the engine's working directory up to its project root, the nearest
directory holding .git, as the binary reads them (`invalid_input:engine_clone:<place>/<entry>`). A
repository that ships skills is refused as well until a role lists them (VELDO-0127). Nothing is deleted;
the factory prepares profiles and the owner removes the file. For another host's engine the working
directory is not known here and its own receiver checks the clone.

**The input.** Codex's `Guard.opening` is the packet whole with the engine's input closed after it; nothing
is held for `release` (VELDO-0155's handshake is Claude Code's).

**The environment strip** is VELDO-0155's wrapper, unchanged for this engine: the five names removed just
before the exec, the run's own empty runtime directory as XDG_RUNTIME_DIR, the receiver's environment kept.

## What the binary's strings say, and what they leave open

Read from the bytes of 0.154.0 (`extract_baseline.py`, `codex-baseline.json`, each anchor the exact text):
the two exec options and their help text, the `-c` override, the three configuration keys with their
values and the packaged defaults (`project_doc_max_bytes = 32768`, `cli_auth_credentials_store = "file"`),
the eight `login status` lines, the engine's refusal message and the hook event names. Not shown by them,
filed for the owner at first: whether the account profile's own AGENTS.md loads under the baseline, and
whether a hooks.json beside a configuration layer is dropped by `--ignore-user-config`. The review of
2026-09-26 answered both with the binary's own offline renderers (`render_offline.py`, scratch CODEX_HOME
and HOME, no login, no model; `codex-rendered.json`): `codex debug prompt-input` puts the profile's
AGENTS.md and AGENTS.override.md in the prompt under the baseline (hence `profile_problem`), and skills from
CODEX_HOME/skills (the bundled `.system` set the binary installs there), HOME/.agents/skills and the clone's
.agents/skills and .codex/skills unless `skills.include_instructions` is false; `codex app-server` lists the
profile's hooks.json as untrusted, its trust kept in the profile's config.toml, which the baseline ignores.
The feature table shows `apps` on by default and off under `--disable apps`. The hooks row plants the
profile's hook in its config.toml, where the spec's falsifier copies it from.

The check of 2026-09-26 (rv155b) ran the real `codex exec` against a model provider on loopback and read
its model request: a skill the prompt names loads whatever the skills section says. `capture_mentions.py`
(`codex-mentions.json`) records it: the binary itself, scratch CODEX_HOME and HOME, no login, every TCP
connect denied but the one loopback port it serves, each request answered 400 so no model runs. A skill is
planted in each place, with controls where the binary does not read (above the project root, below the
working directory, HOME/.codex/skills beside another CODEX_HOME, a skill added to .system), and every one is
named in the packet the receiver writes. Under the previous baseline all four places and the bundled
imagegen load; under this one the bundled set does not, also when it was installed by an earlier run,
and the four places still do, and under every other switch tried as well (`skills.enabled` false,
`skip_host_skill_discovery` on, `mentions_v2` and `skill_search` off, `project_root_markers` empty, the clone
untrusted). A `skills.config` entry naming one skill's file keeps that one skill out, which is per skill only.
With nothing planted, the baseline and the baseline with `skills.include_instructions` at its default send
the same request with no skills section: once the bundled set is off, that switch is a second layer.

## Suite

`scripts/suites/81_veldo_0156_codex_baseline.py` (`python3 scripts/selftest.py --suite
81_veldo_0156_codex_baseline`). The same real parts as VELDO-0155's suite. The engine is a fake Codex laid
out as the vendor package and qualified by the production writer; what it loads is the binary's gate
table written into it: the profile's config.toml unless `--ignore-user-config`, the profile's and the
clone's rules unless `--ignore-rules`, the clone's AGENTS.md unless the budget is 0, the hooks of its
effective configuration, the login of the profile's auth.json (a fixture naming only the kind of login)
unless the store is not the file, the refusal of an API-key login under the forced ChatGPT method, the
profile's instruction files, the skills of the four places and the bundled set (unless
`skills.bundled.enabled` is false) in its skills section unless `skills.include_instructions` is false, and,
whatever that says, the body of each such skill the prompt names in its model request (recorded before its
first turn), and the login's connectors unless apps is disabled; it answers `login status` with the binary's
own lines. Every run's prompt names each planted skill and the bundled set.
