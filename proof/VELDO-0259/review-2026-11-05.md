## Findings

F1 (AC2, correctness/security, must fix). scripts/check_personal_setup.py:160-162. `_diff_added` takes the
file name only from a `+++ b/` header. Git C-quotes some names (non-ASCII, a double quote, a backslash), and
those come through as `+++ "b/..."`. In that case `rel` is None and every added line of the file is skipped.
Reproduced: one commit adds three files, each with a home path, and only the plain-named file is refused.
A candidate can get past the stage just by naming a file that way. Fix: run the diff with
`-c core.quotePath=false` and unquote a C-quoted header, or list the changed files with
`--name-only -z` and diff each one.

F2 (AC2, correctness, should fix). scripts/check_personal_setup.py:166-172 and 181-185. The base is only ever
looked up as origin/main, main, origin/master or master. When none of them resolves, the gate judges only
uncommitted changes, so a committed personal value passes with exit 0 and nothing says the base was missing.
Reproduced in a repository whose trunk is called `trunk`. The lander accepts any trunk name
(.veldo/lander.py:372), and the spec's observability asks for the check to account for what it ran. In this
repository the trunk is main, and the lander pins refs/remotes/origin/main to the watermark
(.veldo/lander.py:565), so landing here is covered today. Fix: when the repository has commits and no base
resolves, print that and exit 2, or let verify.sh pass the trunk through.

F3 (AC1 as written, partly delivered). AC1 asks for "Product defaults name nobody: the spec owner field holds a
role id, an action that needs a person resolves it through the installation, and when the value is absent it
refuses by name". The reader provides owner(), git_identity(), approvers(), channel() and account(), and
they refuse correctly. But nothing in the product calls any of them. The only consumers are the two trace
calls (.veldo/control_factory_setup.py:1644, .veldo/control_service.py:1617). The spec owner field is not
checked as a role id. Owner values are still hard-coded in the tree: scripts/migrate_to_veldo.py:191-197 sets
the owner's name and a personal email as the commit identity, and .veldo/naming.py:78,
.veldo/action_executor.py:871, .veldo/incident_reconcile.py:848 and .veldo/tracker_intake.py:701 carry the
owner's login as a value (all mirrored under engine/.veldo/). There is also the spec frontmatter owner field
across specs/. The AC1 falsifier names landing commit identity, approval records, notifications and
generated specs, and no row exercises any of them. ac1/traces and ac2/product-clean compare only against
invented fixture values, which the product could never contain, so they are vacuous against that falsifier.
This overlaps the spec's Out of scope ("rewriting live files generically ... VELDO-0250"), so the owner
should choose one of two things: wire the person-needing actions (at least landing identity and approval
record) through the reader with installation_missing:owner, or amend AC1 so the consumer cutover is
explicitly VELDO-0250/0253's and this ticket's AC1 is the reader, the resolution and the traces.

## Landing ruling: the home-path rule

What the stage refuses, from the code (rules() and _builtin(), check_personal_setup.py:74-114):
- With no installation, and with an installation whose patterns/ folder is empty, the rule set is the same
  four built-ins. The only difference is that an empty but present folder suppresses the "built-in shapes
  only" line.
- With patterns present, each installation pattern is added on top of the built-ins, with its own category.
- The built-ins apply with or without an installation:
  - home_path: any `/home/<x>`, `/Users/<x>` or `C:\Users\<x>` on any added line of any file, proof/
    included.
  - login_uid: `/run/user/N`, `user-N.slice`, `user@N.service`.
  - fixture_email: a non-reserved email, but only in a fixture path (suites/, tests/, test/, testdata/,
    fixture*, test_*).
  - secret: the existing scanner's shapes, minus the inventory's dispositions.
- The owner's name and a personal email outside fixture paths are NOT refused without an installation
  pattern. Only the home-path shape (which carries a login name) catches identity without one.

Measured with an empty installation, in gate mode against main:
- veldo-0234-0235: 0 findings.
- veldo-0241: 3, and veldo-0248: 3. All six are home_path, all in proof/VELDO-0248/registry/*.json (the
  pip report captures).
- veldo-0253: 0, and veldo-0250: 0.
- Anything built on 0248 inherits those three files. The conversation batch branch was not identified by
  name, so it was not measured.

So landing 0259 first blocks 0241 and 0248, and the builds on them, until those three lines are redacted.
Future proofs are not all refused, only those whose added lines contain a home path. But that is the common
case today: 9 of the last 15 proof directories on main, and 54 of 316 overall, carry one, mostly through
logs and tracebacks of worktrees that live under the home directory.

What the spec requires: AC2 lists "an absolute path under any user's home directory" as a built-in rule over
"the lines a candidate adds", with no exemption for proof/. VELDO-0250's footprint includes proof/**, so a home
path in a proof is exactly the "something new to clean" that 0259 exists to prevent. The refusal is the
specified behaviour, not a defect.

Smallest change that keeps the intent, with no change to the check:
1. Order. Land 0234/0235, 0241 and 0248, plus whatever is already built on them, before 0259. The spec
   only orders 0259 ahead of 0251/0252/0253, so this is allowed. Their three files then sit in 0250's
   scrub inventory with everything else that is pre-split.
2. From then on, builders record paths relative to the repository, or write $HOME as `~` when they capture
   logs (one substitution, for example sed "s#$HOME#~#g"). `~/...` does not match the shape.
3. Do not exempt proof/. That would reopen the leak the stage exists to close. If 0259 must land first, a
   single redaction commit on 0248 for the three JSON files (and its proof re-manifested), picked up by
   0241, is the alternative.
